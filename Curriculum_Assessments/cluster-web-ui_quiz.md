# Cluster Web UI - Senior-Level Assessment

## Section 1: True/False Questions (10 Questions)

1. **Question:** The TaskScheduler directly updates the Spark Web UI state store to ensure millisecond-level precision of task execution times.
   **Answer:** False
   **Mastery Explanation:** The TaskScheduler does not directly update the UI. Doing so would couple distributed scheduling with UI rendering latency. Instead, it posts asynchronous events to the `LiveListenerBus`.

2. **Question:** If the `LiveListenerBus` queue overflows during highly parallel micro-batch streaming, it will intentionally drop events rather than blocking the Driver JVM.
   **Answer:** True
   **Mastery Explanation:** The bus is designed to protect the critical path of the Driver. If event processing falls behind, it drops events (logging a warning) to prevent Driver lockup, causing the UI to permanently miss updates.

3. **Question:** The Spark History Server reads the same RocksDB/LevelDB state store files generated by the live Driver to render historical UIs.
   **Answer:** False
   **Mastery Explanation:** The History Server parses a monolithic JSON event log file created by the `EventLoggingListener`. It replays these events to rebuild the in-memory state from scratch.

4. **Question:** Under Adaptive Query Execution (AQE), stages that appear as "Skipped" or "Cancelled" in the UI are always indicative of failed tasks requiring recomputation.
   **Answer:** False
   **Mastery Explanation:** In Spark 3.x with AQE, dynamically cancelled or skipped stages are often the visual signature of physical plan optimization mid-flight (e.g., converting a Sort-Merge Join to a Broadcast Hash Join), not a task failure.

5. **Question:** Decreasing `spark.ui.retainedTasks` will reduce the memory footprint of the Driver JVM during live application execution.
   **Answer:** True
   **Mastery Explanation:** Retained entities bound the `AppStatusListener` in-memory state. Lowering this value allows the Driver to aggressively evict older task metadata, mitigating Garbage Collection pressure and OOM risks.

6. **Question:** The Tungsten execution engine pushes hardware-sympathetic metrics to the Driver via periodic heartbeats containing `TaskMetrics` objects.
   **Answer:** True
   **Mastery Explanation:** Executors propagate memory, CPU, and shuffle metrics back to the Driver via standard heartbeats, which the LiveListenerBus then merges into the UI's state store.

7. **Question:** You must rely on the Spark Web UI HTML frontend to detect data skew because the underlying REST APIs do not expose task-level metrics like `executorRunTime`.
   **Answer:** False
   **Mastery Explanation:** The Web UI is just an HTML wrapper over a comprehensive REST API. You can query `/api/v1/applications/{app_id}/stages/{stage_id}/0/taskList` to programmatically extract `executorRunTime` and identify skew mathematically.

8. **Question:** Custom `SparkListener` implementations can be registered using `spark.extraListeners` to intercept execution events for real-time alerting.
   **Answer:** True
   **Mastery Explanation:** Elite engineers use this exact integration point to bypass the HTML UI and build custom observability pipelines (e.g., streaming physical metrics directly to Datadog or Prometheus).

9. **Question:** In modern Spark versions, the `AppStatusListener` can offload its materialized view to an embedded LevelDB/RocksDB instance to reduce GC pressure.
   **Answer:** True
   **Mastery Explanation:** To prevent History Server and Driver OOMs, Spark utilizes embedded KV stores like LevelDB/RocksDB to hold the massive UI state rather than keeping it all as raw Java heap objects.

10. **Question:** Rolling event logs (`spark.eventLog.rolling.enabled`) are an anti-pattern that slows down the History Server and should be avoided in production.
    **Answer:** False
    **Mastery Explanation:** Rolling event logs are critical for massive, long-running jobs. They prevent the event log from becoming a massive monolithic JSON blob that would crash the History Server with an OOM when parsed.

## Section 2: Multiple Choice Questions (15 Questions)

11. **Which component is primarily responsible for decoupling high-speed scheduling from view rendering?**
    A) DAGScheduler
    B) AppStatusListener
    C) LiveListenerBus
    D) EventLoggingListener
    **Answer:** C
    **Mastery Explanation:** The `LiveListenerBus` acts as an asynchronous, multi-queue dispatcher that queues events generated by the schedulers and delegates them to listener threads, decoupling the critical path.

12. **What is the primary role of the `FsHistoryProvider`?**
    A) To serialize live events into JSON logs and write them to HDFS.
    B) To serve as an embedded web server in the Driver JVM.
    C) To parse persistent JSON log files and replay the event stream to reconstruct the `AppStatusListener` state.
    D) To push heartbeats from Worker Executors to the Driver.
    **Answer:** C
    **Mastery Explanation:** The `FsHistoryProvider` operates inside the standalone History Server. It reads the historical JSON logs and deterministically replays them to rebuild the UI state for post-mortem debugging.

13. **An engineer notices that a long-running streaming application keeps crashing the Driver with OOM errors. Which configuration is most likely misconfigured?**
    A) `spark.sql.shuffle.partitions`
    B) `spark.eventLog.dir`
    C) `spark.ui.retainedTasks`
    D) `spark.scheduler.mode`
    **Answer:** C
    **Mastery Explanation:** In bounded or long-running applications, failing to strictly limit `spark.ui.retainedTasks` (and Jobs/Stages) causes the `AppStatusListener` state to grow infinitely, bloating the Driver heap until an OOM occurs.

14. **In Spark 3.x with AQE enabled, what does a "Cancelled" stage in the Web UI typically represent?**
    A) A node failure that triggered a stage abort.
    B) A stage skipped due to dynamic planning optimization (e.g., changing join strategies).
    C) A preempted task due to YARN resource revocation.
    D) A data skew failure.
    **Answer:** B
    **Mastery Explanation:** AQE dynamically alters the physical plan mid-flight. When it optimizes a plan, original static stages are visually marked as "Cancelled" or "Skipped" in the UI, replacing them with new execution branches.

15. **If you want to automatically assert that a specific code commit did not cause a regression in memory spill, what is the most robust approach?**
    A) Use Selenium to scrape the Web UI HTML in the CI pipeline.
    B) Parse the Driver text logs using Regex for "spill" keywords.
    C) Query the internal History Server REST API (`/api/v1/applications/{app_id}/stages`) to evaluate `diskBytesSpilled`.
    D) Enable `spark.memory.fraction=1.0`.
    **Answer:** C
    **Mastery Explanation:** The REST API provides a structured, JSON-based payload of physical metrics. Querying this programmatically is the elite way to enforce performance SLA budgets in CI/CD.

16. **Which listener is primarily responsible for establishing the persistent audit trail required for History Server reconstruction?**
    A) AppStatusListener
    B) HeavyShuffleDetectorListener
    C) DAGScheduler
    D) EventLoggingListener
    **Answer:** D
    **Mastery Explanation:** The `EventLoggingListener` intercepts bus events and serializes them using Spark's `JsonProtocol` into a continuous JSON event log file on persistent storage.

17. **What happens if a custom `SparkListener` throws an unhandled exception inside its `onTaskEnd` method?**
    A) The Task is marked as failed and retried.
    B) The entire Spark job is aborted.
    C) The listener thread catches it, logs an error, and drops the event, but does not crash the Driver JVM.
    D) The Executor JVM crashes.
    **Answer:** C
    **Mastery Explanation:** The `LiveListenerBus` catches exceptions thrown by listeners in their dedicated dispatcher threads. It logs an error but ensures that a poorly written listener does not crash the DAGScheduler or Driver.

18. **When the History Server processes a massive JSON event log, its startup computational complexity is roughly proportional to:**
    A) The size of the raw input data partitions.
    B) The total number of execution events generated by the application.
    C) The number of Worker nodes in the cluster.
    D) The available RAM on the History Server.
    **Answer:** B
    **Mastery Explanation:** History Server replay complexity is O(N) where N is total events. Parsing massive JSON event logs is heavily CPU-bound and memory-intensive, leading to high startup latency.

19. **Which metric within `TaskMetrics` is most statistically reliable for computationally identifying structural data skew?**
    A) `jvmGCTime`
    B) `executorCpuTime`
    C) `executorRunTime` correlated with `shuffleReadMetrics.recordsRead`
    D) `resultSerializationTime`
    **Answer:** C
    **Mastery Explanation:** Skew is characterized by a massive discrepancy in data processing. Correlating anomalous wall-clock execution time (`executorRunTime`) with extreme shuffle record ingestion (`recordsRead`) confirms skew.

20. **Why is configuring `spark.eventLog.rolling.enabled=true` critical for large-scale enterprise pipelines?**
    A) It enables real-time WebSocket streaming to the Web UI.
    B) It allows the History Server to parse smaller chunks, preventing it from OOMing on a single monolithic multi-gigabyte JSON blob.
    C) It compresses the logs using Snappy to save disk space.
    D) It automatically deletes older applications from the History Server.
    **Answer:** B
    **Mastery Explanation:** Without rolling logs, a massive application yields a single enormous JSON file. The History Server must load it entirely to parse it, resulting in catastrophic OOM failures.

21. **To guarantee that a custom `SparkListener` intercepts early events like `SparkListenerApplicationStart`, how must it be registered?**
    A) `spark.sparkContext.addSparkListener(new MyListener())`
    B) Through the Web UI "Configuration" tab.
    C) Setting `spark.extraListeners` in the SparkSession configuration.
    D) By overriding the `DAGScheduler` class.
    **Answer:** C
    **Mastery Explanation:** Attaching via context occurs *after* initialization. `spark.extraListeners` ensures instantiation before the `DAGScheduler` begins emitting critical startup events.

22. **In the REST API for Task Lists, why is the response length heavily bounded (e.g., `?length=10000`)?**
    A) JSON syntax restricts array sizes to 10k elements.
    B) To prevent the REST server and History Server JVM from running out of memory when serializing massive task graphs.
    C) Because a Spark stage cannot have more than 10k tasks.
    D) Because the LiveListenerBus drops any task after 10k.
    **Answer:** B
    **Mastery Explanation:** Returning a JSON array of 100,000 deep task metric objects requires massive Java heap allocation for serialization, guaranteeing an API-induced OOM.

23. **If the Web UI's "Executors" tab shows high GC time, what is the best immediate course of action for deep debugging?**
    A) Increase `spark.ui.retainedTasks`.
    B) Disable AQE.
    C) Enable detailed JVM GC logging via `spark.executor.extraJavaOptions="-verbose:gc"`.
    D) Write a custom SparkListener to kill tasks with high GC.
    **Answer:** C
    **Mastery Explanation:** High GC time in the UI is a symptom. To diagnose memory leaks or young-gen/old-gen thrashing, you must push detailed GC logs to the executor `stdout/stderr` using JVM flags.

24. **How are Tungsten execution metrics (like `diskBytesSpilled`) transported from Executors to the UI?**
    A) Sent immediately via a synchronous RPC call upon byte spill.
    B) Piggybacked asynchronously on periodic Executor-to-Driver heartbeats.
    C) Written to HDFS by the Executor and read by the Driver.
    D) Broadcasted via Zookeeper.
    **Answer:** B
    **Mastery Explanation:** To minimize network overhead, task metrics are periodically aggregated and attached to the standard heartbeat payloads sent to the Driver.

25. **When building automated alerting based on the UI REST API, why must you filter out tasks where `status != 'SUCCESS'` when calculating data skew percentiles?**
    A) Failed tasks are not recorded by the AppStatusListener.
    B) Killed speculative tasks or immediate task failures have runtime durations near zero, which mathematically distorts the baseline percentiles.
    C) Failed tasks do not have a `taskMetrics` block in the JSON.
    D) The API returns HTTP 500 if you process failed tasks.
    **Answer:** B
    **Mastery Explanation:** Speculative execution or immediate OOM failures yield tiny execution times. Including them artificially lowers the median/75th percentile, creating false-positive skew alerts.

## Section 3: "Small Twist" Scenario Questions (15 Questions)

26. **Scenario:** You configure `spark.ui.retainedTasks = 10`. You run a stage with 100 tasks. You then query the REST API for the task-list of that stage.
    **Twist:** How many tasks are returned by the API?
    **Answer:** Only the last 10 tasks.
    **Mastery Explanation:** The REST API queries the exact same `AppStatusListener` in-memory state store as the HTML UI. Bounding the retention bounds the API visibility.

27. **Scenario:** You configure `spark.eventLog.enabled = true`, but forget to set `spark.eventLog.dir`.
    **Twist:** What happens when you submit the application?
    **Answer:** The Spark context fails to initialize and the application crashes on startup.
    **Mastery Explanation:** The event logging subsystem strictly requires a target directory. Without it, the `EventLoggingListener` throws a fatal configuration exception.

28. **Scenario:** AQE is enabled. A SortMergeJoin is planned. Runtime stats reveal one side is tiny. AQE alters the physical plan to a BroadcastHashJoin.
    **Twist:** When looking at the "SQL" tab DAG, do you see the SMJ or BHJ?
    **Answer:** You see the SMJ node marked as skipped/cancelled, and a dynamically injected BHJ node alongside it.
    **Mastery Explanation:** AQE does not delete history; it visualizes the dynamic transition so engineers can audit the exact optimizations Catalyst applied at runtime.

29. **Scenario:** The LiveListenerBus drops events due to severe queue overflow during micro-batching.
    **Twist:** What happens to the actual physical Spark job execution (e.g., writing data)?
    **Answer:** Nothing. The job continues to execute normally.
    **Mastery Explanation:** The architecture heavily prioritizes execution over observability. Event drops simply result in missing progress bars or metrics in the UI, not job failure.

30. **Scenario:** You are analyzing a stage in the Web UI. The maximum task duration is 15 minutes, but the median is 4 seconds.
    **Twist:** You check `diskBytesSpilled` and `memoryBytesSpilled`, and both are zero. What is the likely cause?
    **Answer:** Computation-bound data skew, or skew on a key where the grouped values still fit entirely in memory (e.g., massive UDF processing on a single heavily-skewed key).
    **Mastery Explanation:** Skew does not always trigger spills. If the operation is CPU-heavy (like JSON parsing or complex regex) on a skewed partition, execution time skyrockets without memory pressure.

31. **Scenario:** You have a CI script that queries `/api/v1/applications/{app_id}/stages`. You run the script while the job is actively running on the cluster, and then again a week later.
    **Twist:** Is there a difference in the base URL port for the two runs?
    **Answer:** Yes. The live run queries the Driver (port 4040). The historical run queries the History Server (port 18080).
    **Mastery Explanation:** The REST API endpoints are identical, but they are served by different JVMs depending on application lifecycle state.

32. **Scenario:** You decrease `spark.sql.ui.retainedExecutions` to 5. A pipeline runs 10 complex SQL queries.
    **Twist:** Does this configuration delete the actual underlying Parquet output of the first 5 queries?
    **Answer:** No. 
    **Mastery Explanation:** UI retention configurations strictly govern the metadata used for UI rendering and History Server state. They have zero impact on physical data materialization or HDFS/S3 storage.

33. **Scenario:** Your executors are configured to send heartbeats every 10 seconds. You are watching a long-running task in the Web UI.
    **Twist:** How often do metrics like `recordsRead` increment on your screen?
    **Answer:** Every 10 seconds (when the heartbeat arrives).
    **Mastery Explanation:** Metrics are not continuously streamed; they are bundled into heartbeats. The UI only updates when the Driver processes these heartbeats from the LiveListenerBus.

34. **Scenario:** A task fails 3 times due to a network timeout and succeeds on the 4th retry.
    **Twist:** How many `SparkListenerTaskEnd` events are published to the LiveListenerBus?
    **Answer:** 4 events.
    **Mastery Explanation:** Every task attempt, whether successful or failed, emits an end event with its respective terminal state and metrics.

35. **Scenario:** You use the REST API to enforce an SLA on `executorCpuTime` vs `executorRunTime`. 
    **Twist:** Are these two metrics identical for a CPU-bound task?
    **Answer:** No. `executorRunTime` is wall-clock time. `executorCpuTime` is JVM CPU nanos.
    **Mastery Explanation:** Even in CPU-bound tasks, `executorRunTime` includes time spent waiting for thread scheduling, GC pauses, or minor I/O blocking. CPU time is always strictly less than or equal to Run time.

36. **Scenario:** You have `spark.ui.retainedJobs=100000` on an unbounded streaming job. The driver crashes with OOM.
    **Twist:** You increase Driver memory from 16GB to 64GB. What is the long-term result?
    **Answer:** The driver will eventually OOM again or suffer catastrophic GC pauses.
    **Mastery Explanation:** Increasing heap simply delays the inevitable. Unbounded retention in a streaming context guarantees a memory leak. Strict limits must be enforced.

37. **Scenario:** The History Server displays an application, and the "Jobs" tab shows 50 completed jobs, but the "Stages" tab is completely empty.
    **Twist:** Why might Stages be missing while Jobs are visible?
    **Answer:** `spark.ui.retainedStages` is configured extremely low, or stages were aggressively evicted from the state store while jobs remained within their retention threshold.
    **Mastery Explanation:** Jobs and Stages have independent retention configurations. A stage can be evicted from memory while its parent Job metadata is retained.

38. **Scenario:** You write a custom SparkListener and attach it via `spark.extraListeners`. Inside `onJobStart`, you execute a heavy database query taking 5 seconds.
    **Twist:** What happens to the Spark UI?
    **Answer:** The UI becomes unresponsive or heavily delayed for 5 seconds per job.
    **Mastery Explanation:** Listener callbacks are executed on the bus dispatcher thread. Blocking operations in a listener pause event dispatching, leading to queue backups and delayed UI rendering.

39. **Scenario:** You run Spark in standalone cluster mode. You set `spark.eventLog.dir` to `/tmp/spark-events` (a local filesystem path).
    **Twist:** Why will the History Server fail to show the job?
    **Answer:** The Driver writes to its local `/tmp`, but the History Server (running on a different physical node) cannot access that local disk.
    **Mastery Explanation:** Event logs must be written to a globally accessible, shared filesystem (like HDFS, S3, or NFS) so the standalone History Server daemon can read them.

40. **Scenario:** You explicitly disable AQE Skew Join Optimization (`spark.sql.adaptive.skewJoin.enabled = false`) and data skew occurs. 
    **Twist:** How will the UI reflect this visually in the Stages tab?
    **Answer:** One specific task will have a massive `executorRunTime` and `shuffleReadMetrics.recordsRead` compared to the median, and the stage progress bar will hang at 99%.
    **Mastery Explanation:** Without AQE to dynamically split the skewed partition, the physical execution reverts to traditional static hashing, manifesting as the classic "straggler task" signature in the UI.

## Section 4: Coding & Debugging Questions (10 Questions)

41. **Bug Identification:**
    ```scala
    // Custom Listener aiming to track shuffle writes
    override def onTaskStart(taskStart: SparkListenerTaskStart): Unit = {
      val writeMetrics = taskStart.taskMetrics.shuffleWriteMetrics.bytesWritten
      println(s"Task started writing: $writeMetrics")
    }
    ```
    **Answer/Explanation:** Bug. Task metrics are not populated at `onTaskStart`. They accumulate during execution and are published definitively during `onTaskEnd` (or via heartbeats). `taskMetrics` may be null or zero here.

42. **Bug Identification:**
    ```python
    import requests
    # Job finished 10 minutes ago
    r = requests.get("http://driver-node:4040/api/v1/applications/app_123/stages")
    print(r.json())
    ```
    **Answer/Explanation:** Bug. Port 4040 is hosted by the live Driver JVM. Once the job finishes, the JVM exits and the port dies. You must query the History Server on port 18080 for completed applications.

43. **Bug Identification:**
    ```scala
    val spark = SparkSession.builder()
      .config("spark.ui.retainedTasks", "-1")
      .config("spark.ui.retainedStages", "-1")
      .getOrCreate()
    ```
    **Answer/Explanation:** Bug (Memory Leak). Setting retention to `-1` or unbounded means the `AppStatusListener` will never evict UI metadata. In a production pipeline, this guarantees a Driver OOM exception.

44. **Debugging SLA Logic:**
    ```python
    # CI/CD SLA check script
    for stage in stages:
        if stage['diskBytesSpilled'] > 0:
            print("SLA Failed! Disk spill detected.")
            sys.exit(1)
    ```
    **Answer/Explanation:** Flawed logic. A strictly zero-spill SLA is impossible or highly inefficient for massive datasets. Disk spill is a natural mechanic of external sorting/shuffling. The SLA should assert against a reasonable upper bound threshold (e.g., `> 500MB`), not zero.

45. **Bug Identification:**
    ```scala
    class MyListener extends SparkListener {
      override def onStageCompleted(stageCompleted: SparkListenerStageCompleted): Unit = {
        Thread.sleep(5000) // Simulate heavy processing
      }
    }
    ```
    **Answer/Explanation:** Bug. `Thread.sleep` blocks the LiveListenerBus dispatcher thread. This will rapidly cause the event queue to fill up, forcing the bus to drop subsequent events and blinding the Web UI.

46. **Debugging Missing Logs:**
    ```bash
    spark-submit --conf spark.driver.extraJavaOptions="-verbose:gc" my_job.py
    ```
    *Issue:* You check the Web UI "Executors" tab and click the stdout logs for Executor 2, but see no GC logs.
    **Answer/Explanation:** The configuration `spark.driver.extraJavaOptions` only applies to the Driver JVM. To see GC logs for distributed workers in the UI, you must configure `spark.executor.extraJavaOptions="-verbose:gc"`.

47. **Flawed Skew Calculation:**
    ```python
    # Skew detection logic
    skewed = max(durations) > (2 * min(durations))
    ```
    **Answer/Explanation:** Statistically flawed. The minimum task time could be a speculative task that was killed instantly (e.g., 2ms), making a normal 100ms task look like a 50x skew. Always compare the maximum to the median or 75th percentile.

48. **UI Missing Completely:**
    ```scala
    val spark = SparkSession.builder()
      .config("spark.ui.enabled", "false")
      .config("spark.eventLog.enabled", "true")
      .getOrCreate()
    ```
    *Issue:* An engineer complains port 4040 isn't working, but the History Server shows the job later.
    **Answer/Explanation:** `spark.ui.enabled=false` prevents the Driver from booting the Jetty web server (saving Driver resources). However, `eventLog.enabled=true` means the audit trail is still written to disk, so the History Server can replay it later. This is a valid pattern, not a bug, but explains the missing port 4040.

49. **History Server Crash:**
    *Issue:* History server OOMs repeatedly. The logs show it crashing while parsing `app_9999_eventlog.json`.
    *Solution implementation:*
    ```scala
    // How do you fix the Spark job generating the log?
    .config("spark.eventLog.rolling.enabled", "true")
    .config("spark.eventLog.rolling.maxFileSize", "128m")
    ```
    **Answer/Explanation:** The job generated a monolithic log file too large for the History Server heap. Rolling the logs chunks the file into 128MB segments, allowing the History Server to process and evict segments efficiently, avoiding OOM.

50. **Missing Metrics in Custom Listener:**
    *Issue:* You wrote a custom listener to capture memory spill, but your listener logs print `0` for spilled bytes, while the Web UI shows 5GB spilled.
    **Answer/Explanation:** You are likely extracting metrics from `onTaskStart` or `onStageSubmitted`, where physical metrics haven't occurred yet. Ensure you extract metrics strictly from the `taskMetrics` payload inside the `onTaskEnd` or `onStageCompleted` callback events.
