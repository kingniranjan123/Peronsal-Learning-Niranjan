# SQL Queries (Spark SQL) - Elite Assessment

## 1. True/False Questions (10 Questions)

**1. True or False:** Spark's Catalyst Optimizer's `FilterPushdown` rule can always push filters down to the data source (e.g., Parquet) even if the filter evaluates a user-defined function (UDF) that is non-deterministic.
**Answer:** False
**Mastery Explanation:** Catalyst cannot push down non-deterministic UDFs or UDFs generally to the data source level because data sources evaluate filters at the file/block level, and UDFs are executed within the Spark executor's JVM context. Pushing them down would lead to incorrect results or is simply unsupported by the source reader (like Parquet).

**2. True or False:** When using `spark.sql.adaptive.enabled=true`, AQE can dynamically switch a SortMergeJoin to a BroadcastHashJoin if one of the shuffle partitions sizes falls below the `spark.sql.adaptive.autoBroadcastJoinThreshold`.
**Answer:** True
**Mastery Explanation:** This is one of the primary features of Adaptive Query Execution (AQE). Spark collects runtime statistics after the map stage (shuffle write). If the total size of a relation is smaller than the broadcast threshold, it can dynamically switch the join strategy, avoiding the expensive sort and shuffle read phases of the SortMergeJoin.

**3. True or False:** Tungsten’s whole-stage code generation (WSCG) compiles all physical operators of a query plan into a single Java function to eliminate virtual function calls.
**Answer:** False
**Mastery Explanation:** WSCG fuses multiple operators into a single Java function, but it does NOT fuse *all* operators. Pipeline-breaking operators (like Sort, Aggregate with shuffle, and Join) break the code generation boundaries. A query plan usually consists of multiple WSCG stages.

**4. True or False:** In a Spark SQL query, using `COUNT(DISTINCT column_a)` on a highly skewed dataset is always optimized by Catalyst to use a two-phase aggregation (partial and final) to prevent OutOfMemory errors on a single executor.
**Answer:** True
**Mastery Explanation:** Catalyst implements two-phase aggregation for `COUNT(DISTINCT)` by default. The first phase does a partial aggregation locally on the map side (HashAggregate), and the second phase merges the partial results after a shuffle. However, if the skew is extreme on the distinct keys, a single executor might still become a bottleneck during the final reduce phase.

**5. True or False:** The Cost-Based Optimizer (CBO) in Spark SQL requires table statistics (like row count and column histograms) to be pre-computed via the `ANALYZE TABLE` command to function effectively.
**Answer:** True
**Mastery Explanation:** CBO relies heavily on accurate statistics to estimate cardinalities and cost out different join reorderings. Without `ANALYZE TABLE COMPUTE STATISTICS`, the CBO falls back to rule-based heuristics, as it lacks the necessary data distribution knowledge.

**6. True or False:** A `LEFT SEMI JOIN` will always return exactly the same number of rows as a standard `INNER JOIN` if all join keys are unique in the right table.
**Answer:** True
**Mastery Explanation:** A `LEFT SEMI JOIN` returns rows from the left table where a match exists in the right table. If the keys are unique on the right, an `INNER JOIN` will not duplicate any left-table rows, making the row count identical to a `SEMI JOIN`. However, the `SEMI JOIN` only projects columns from the left table.

**7. True or False:** BroadcastHashJoins are immune to data skew on the large table.
**Answer:** True
**Mastery Explanation:** Because the small table is broadcast to all executors, the large table is processed exactly where its partitions already reside. There is no shuffle required for the large table based on the join key, meaning data skew in the join key does not cause a single task to be overwhelmed by a massive shuffle block.

**8. True or False:** `spark.sql.shuffle.partitions` controls the number of output files produced when writing a DataFrame to storage, regardless of the physical plan.
**Answer:** False
**Mastery Explanation:** `spark.sql.shuffle.partitions` only controls the number of partitions *after a shuffle operation* (like group by or join). If a query has no shuffle operations (e.g., just map/filter), the number of output partitions depends entirely on the input partitions or a subsequent `coalesce()` or `repartition()` operation.

**9. True or False:** The logical plan generated by Spark SQL is unaware of the underlying file formats (like Parquet, ORC, or CSV).
**Answer:** True
**Mastery Explanation:** The logical plan represents the abstract data flow and relational algebra (projections, filters, joins). File format details, block sizes, and partitioning are mapped during the Physical Planning phase when Spark determines the actual execution strategy (e.g., `FileSourceScanExec`).

**10. True or False:** A Full Outer Join can be optimized to use a BroadcastHashJoin strategy in Spark 3.x.
**Answer:** False
**Mastery Explanation:** Spark does not support BroadcastHashJoin for Full Outer Joins. A BroadcastHashJoin requires one side to be small enough to fit in memory, but a Full Outer Join requires keeping track of unmatched rows from *both* sides, which breaks the local hash probe semantics of the broadcast join. SortMergeJoin or ShuffledHashJoin must be used.

## 2. Multiple Choice Questions (15 Questions)

**11. Which Catalyst Optimizer phase is responsible for converting an Unresolved Logical Plan into a Resolved Logical Plan?**
A) Physical Planning
B) Analysis
C) Logical Optimization
D) Query Execution
**Answer:** B
**Mastery Explanation:** The Analysis phase uses the Catalog to resolve table names, column names, and check data types. It transforms the Unresolved Logical Plan (parsed from SQL string) into a Resolved Logical Plan.

**12. When evaluating a query containing multiple joins, how does the Cost-Based Optimizer (CBO) prevent exponential compile times for star schemas with many tables?**
A) It strictly uses a greedy algorithm for all joins.
B) It sets a hard limit on the number of tables to reorder using dynamic programming (`spark.sql.cbo.joinReorder.dp.threshold`).
C) It relies on AQE to fix the join order at runtime.
D) CBO doesn't optimize join order, only join strategies.
**Answer:** B
**Mastery Explanation:** Dynamic programming for join reordering is computationally expensive ($O(3^n)$). Spark bounds this using `spark.sql.cbo.joinReorder.dp.threshold` (default 12). For queries exceeding this number of joins, Spark disables the exhaustive CBO reordering to prevent driver OOM or massive planning delays.

**13. What is the primary advantage of the Tungsten memory format over standard JVM objects?**
A) It allows Spark to use Python objects directly in the JVM.
B) It stores data in off-heap memory, eliminating garbage collection overhead and leveraging CPU cache efficiently.
C) It automatically compresses all strings using Snappy.
D) It converts all data into columnar format internally for map operations.
**Answer:** B
**Mastery Explanation:** Tungsten represents data using a custom binary format (`UnsafeRow`). By bypassing standard JVM objects, it dramatically reduces object creation (preventing GC pauses) and packs data tightly, which aligns well with modern CPU L1/L2 cache lines for vectorized processing.

**14. In a SortMergeJoin, what happens if the data on a single join key exceeds the memory capacity of the executor task?**
A) Spark throws an OutOfMemoryError immediately.
B) Spark spills the rows for that specific join key to disk and streams them during the join.
C) Spark automatically broadcasts the smaller partition to other executors.
D) Spark converts the join to a Cartesian Product.
**Answer:** B
**Mastery Explanation:** SortMergeJoin is designed to be robust against memory limits. The iterator-based model allows it to spill matching rows for a highly skewed key to disk if the buffer (`ExternalAppendOnlyMap`) fills up. This prevents OOM, albeit at the cost of disk I/O performance.

**15. Which of the following SQL functions is a pipeline breaker in Whole-Stage Code Generation?**
A) `UPPER(col)`
B) `COALESCE(col1, col2)`
C) `ROW_NUMBER() OVER (PARTITION BY col1 ORDER BY col2)`
D) `CAST(col AS STRING)`
**Answer:** C
**Mastery Explanation:** Window functions like `ROW_NUMBER()` require sorting and shuffling (Exchange operator) to gather the partition data onto the same executor before calculating the window frame. This physically breaks the generated code pipeline into multiple stages.

**16. What does `spark.sql.autoBroadcastJoinThreshold` default to?**
A) 10 MB
B) 100 MB
C) 1 GB
D) It is disabled by default.
**Answer:** A
**Mastery Explanation:** The default broadcast threshold is 10 MB (`10485760` bytes). Tables estimated to be under this size will be broadcasted. Setting it to -1 disables broadcast joins.

**17. You are analyzing a Spark UI SQL tab and notice an `Exchange hashpartitioning` node. What triggered this?**
A) A map-side broadcast
B) A shuffle operation caused by a `GROUP BY` or `JOIN`
C) A cache materialization
D) File reading from Parquet
**Answer:** B
**Mastery Explanation:** `Exchange` is Spark's physical operator for a Shuffle. `hashpartitioning` indicates the data is being repartitioned across executors using a hash of specific keys, which is the standard prerequisite for aggregations or joins (unless the data is already co-partitioned).

**18. What is the purpose of the `LocalLimit` operator in a query plan?**
A) To enforce a global `LIMIT` clause across all partitions.
B) To limit the number of rows read from each individual executor partition before shuffling.
C) To restrict memory usage per core.
D) To limit the number of files read from HDFS/S3.
**Answer:** B
**Mastery Explanation:** When you write `LIMIT n`, Catalyst optimizes this by placing a `LocalLimit n` on each partition *before* the shuffle (Exchange), and a `GlobalLimit n` after. This drastically reduces the amount of data shuffled.

**19. How does Spark handle `NULL` values in join keys for a standard `INNER JOIN`?**
A) Rows with `NULL` keys are joined to other rows with `NULL` keys.
B) Rows with `NULL` keys are dropped entirely.
C) `NULL` keys cause a runtime exception.
D) `NULL` is treated as an empty string.
**Answer:** B
**Mastery Explanation:** In SQL semantics, `NULL = NULL` evaluates to `UNKNOWN` (essentially False). Therefore, an inner join condition on keys containing `NULL` will fail, and those rows are dropped. Catalyst actively injects an `IsNotNull` filter during optimization to drop these rows early.

**20. Which metric is most critical when debugging a skewed SortMergeJoin in the Spark UI?**
A) Number of Output Rows
B) Peak Execution Memory
C) Shuffle Read Size / Records per Task
D) GC Time
**Answer:** C
**Mastery Explanation:** Data skew manifests as one or a few tasks reading significantly more data than the others during the shuffle phase. Monitoring the Max vs. Median "Shuffle Read Size" or "Records" in the stage details is the definitive way to identify skew.

**21. What happens when `spark.sql.files.maxPartitionBytes` is larger than the actual Parquet block size?**
A) Spark splits the block, causing read errors.
B) Spark packs multiple Parquet blocks into a single partition for the task to read.
C) Spark ignores the setting and uses the Parquet block size.
D) The query throws an IllegalArgumentException.
**Answer:** B
**Mastery Explanation:** This config controls how much data a single partition should process. If it's larger than the file's block size (or the entire file), Spark's `FilePartition` will group multiple blocks/files into a single task to reduce the total number of tasks, improving efficiency for many small files.

**22. In AQE, what does "Coalescing Shuffle Partitions" do?**
A) It reduces the number of initial shuffle partitions dynamically to avoid small tasks.
B) It combines multiple shuffle stages into one.
C) It replaces `repartition()` with `coalesce()` in the logical plan.
D) It merges small files on disk after the query finishes.
**Answer:** A
**Mastery Explanation:** If you set `spark.sql.shuffle.partitions=200`, but a query processes very little data, AQE will notice that the post-shuffle partitions are tiny. It will dynamically combine these small, contiguous partitions into fewer, optimally sized partitions (based on `spark.sql.adaptive.advisoryPartitionSizeInBytes`) before scheduling the reduce tasks.

**23. Why is `ShuffledHashJoin` sometimes preferred over `SortMergeJoin`?**
A) It requires less memory.
B) It avoids the $O(N \log N)$ sorting overhead if one side is small enough to build a local hash map, but too large for a broadcast.
C) It is the only join type that supports Full Outer Joins.
D) It prevents data skew completely.
**Answer:** B
**Mastery Explanation:** `SortMergeJoin` requires sorting both sides, which is expensive. If one partition side can fit into executor memory after a shuffle, a `ShuffledHashJoin` can build a hash table on the smaller side and probe it with the larger side in $O(N)$ time, skipping the sort.

**24. When writing a UDF in Python (PySpark) vs. a Scala UDF, what is the primary performance bottleneck?**
A) Python UDFs cannot use Catalyst type casting.
B) Data must be serialized/deserialized between the executor JVM and Python worker processes via sockets.
C) Python UDFs disable Whole-Stage Code Generation for the entire query.
D) Python UDFs only run on the driver node.
**Answer:** B
**Mastery Explanation:** Standard PySpark UDFs require data to be extracted from Tungsten format, serialized (using Pickle), sent over a socket to a Python daemon, processed, serialized back, and converted back to Tungsten. This serialization overhead is massive. Vectorized Pandas UDFs (Arrow) mitigate this.

**25. What is the role of `spark.sql.optimizer.maxIterations`?**
A) Limits the number of times a recursive CTE can loop.
B) Limits the number of times Catalyst applies its rule batches to reach a fixed point.
C) Limits the depth of the physical plan tree.
D) Limits the maximum number of rows a query can process.
**Answer:** B
**Mastery Explanation:** Catalyst applies optimization rules in batches. Some batches are applied iteratively until the plan stops changing (a "fixed point"). To prevent infinite loops if rules contradict each other, this parameter bounds the maximum number of iterations (default 100).

## 3. "Small Twist" Questions (15 Questions)

**26. Scenario:** Query A joins Table X (100 GB) and Table Y (5 MB) using an equi-join on `id`. It executes as a `BroadcastHashJoin`.
**Twist:** You change the join condition from `X.id = Y.id` to `X.id > Y.id`. What happens to the physical plan?
**Answer:** It degrades to a `BroadcastNestedLoopJoin`.
**Mastery Explanation:** Hash joins (Broadcast or Shuffled) absolutely require an equi-join condition (`=`) to build and probe the hash map. Inequality joins (`>`, `<`, `BETWEEN`) cannot use hash maps. Spark must broadcast the small table and do a nested loop iteration over every row for every row in the large table, which is extremely slow ($O(M \times N)$).

**27. Scenario:** A query aggregates data: `SELECT store, SUM(sales) FROM data GROUP BY store`. The data is highly skewed by `store`. The execution time is 10 minutes.
**Twist:** You change the query to `SELECT store, SUM(sales), PERCENTILE_APPROX(sales, 0.5) FROM data GROUP BY store`. What happens to the execution characteristics?
**Answer:** The executor running the skewed `store` key will likely throw an OutOfMemoryError or spill heavily, significantly increasing runtime.
**Mastery Explanation:** `SUM` is an algebraic aggregation function; Catalyst can do a partial sum on the map side, meaning only a few rows per store are shuffled. `PERCENTILE_APPROX` is a holistic function; it cannot be partially aggregated easily in the same way. All raw values for a single store must be shuffled to one executor, blowing up memory usage for skewed keys.

**28. Scenario:** You set `spark.sql.shuffle.partitions = 1000`. You run a query that filters data, and saves it: `df.filter(col("val") > 10).write.parquet("s3://...")`.
**Twist:** You expect 1000 files to be written, but only 10 files are written. Why?
**Answer:** There was no shuffle boundary in the query.
**Mastery Explanation:** A simple `filter` operation is a narrow dependency (map-only). It does not trigger a shuffle. Therefore, `spark.sql.shuffle.partitions` is completely ignored. The number of output files is determined by the number of input partitions (which was likely 10).

**29. Scenario:** You run `spark.read.parquet("path").count()`. The query finishes in 1 second by utilizing Parquet metadata.
**Twist:** You change it to `spark.read.parquet("path").filter("val > 0").count()`. It now takes 5 minutes. Why the massive difference?
**Answer:** The filter forced Spark to scan the actual data files rather than relying solely on file/row-group metadata.
**Mastery Explanation:** A pure `.count()` without filters can often be answered just by reading the Parquet file footers (which store row counts). Once a filter is introduced, Spark must physically read the columns, decode them, and apply the filter row-by-row before counting, which requires massive I/O.

**30. Scenario:** You enable AQE `spark.sql.adaptive.enabled=true` and run a SortMergeJoin. You see it dynamically convert to a BroadcastHashJoin.
**Twist:** You add a `.cache()` to the DataFrame right before the join action. AQE no longer converts the join. Why?
**Answer:** Caching breaks AQE's ability to re-plan past the cache boundary in some Spark versions, or the size estimation of the cached RDD is inaccurate.
**Mastery Explanation:** When a DataFrame is cached (using `InMemoryTableScanExec`), Spark often uses the logical plan size estimates rather than runtime map-stage statistics. If the logical size is over the broadcast threshold, AQE might not confidently convert it because the physical map-stage metrics (which AQE relies on) are hidden behind the cache materialization.

**31. Scenario:** You are joining two massive tables, A and B, on a skewed `user_id`. You enable AQE skew optimization: `spark.sql.adaptive.skewJoin.enabled=true`. The skew is resolved, and performance improves.
**Twist:** You change the join type from `INNER JOIN` to `LEFT OUTER JOIN` (where A is the left, skewed table). AQE skew optimization fails to trigger. Why?
**Answer:** AQE skew join optimization cannot split skewed partitions on the outer side of an outer join.
**Mastery Explanation:** Skew optimization works by splitting the skewed partition of one table and duplicating the corresponding partition of the other table. However, in a Left Outer Join, if you split the left (outer) side, you might generate duplicate NULL-padded rows for unmatched keys across the splits. Thus, Spark disables skew optimization for the outer side.

**32. Scenario:** You read a CSV file using `spark.read.csv()`. You notice all columns are strings, so you explicitly cast them: `df.withColumn("id", col("id").cast("int"))`.
**Twist:** Instead of casting, you supply a user-defined schema to `spark.read.schema(my_schema).csv()`. The read performance improves dramatically. Why?
**Answer:** Supplying a schema prevents Spark from running a preliminary job to infer the schema.
**Mastery Explanation:** If no schema is provided for CSV/JSON, Spark runs a full separate job over a sample (or all) of the data just to infer data types. Providing the schema skips this entirely. Furthermore, casting down the line forces string creation first, while reading directly with a schema parses directly to the target Tungsten type.

**33. Scenario:** You are writing data to Parquet partitioned by `date`: `df.write.partitionBy("date").parquet("out")`. The data has 30 days of data and 100 Spark partitions. It creates 3,000 files.
**Twist:** You add a sort before writing: `df.sortWithinPartitions("date").write.partitionBy("date").parquet("out")`. How does the number of files change?
**Answer:** The number of files drops significantly, likely close to 30 or 100, depending on data distribution.
**Mastery Explanation:** Without sorting, a single task processes rows in random order. Every time it encounters a new `date`, it opens a new file handle (or keeps many open, writing small chunks). By sorting within partitions by the partition key, each task writes contiguous blocks for a single date, closes the file, and moves to the next, drastically reducing the small file problem.

**34. Scenario:** A query plan uses `Project [A, B]`. It executes efficiently.
**Twist:** You add a UDF to the projection: `Project [A, my_udf(B)]`. The execution time spikes, and the physical plan shows `BatchEvalPython`. What happened?
**Answer:** The Python UDF forced data out of the Tungsten JVM space.
**Mastery Explanation:** `BatchEvalPython` indicates a standard PySpark UDF. Spark had to extract the Tungsten rows, serialize them, pipe them to the Python worker, execute the UDF, pipe back, and deserialize. This breaks WSCG and destroys vectorization benefits.

**35. Scenario:** You do `df1.join(df2, "id")` where `df2` is 5MB. Spark automatically broadcasts `df2`.
**Twist:** `df2` is created via a complex calculation: `df1.groupBy("id").count()`. Spark decides to do a SortMergeJoin instead of Broadcast. Why?
**Answer:** The CBO couldn't estimate the size of the aggregated result accurately.
**Mastery Explanation:** Spark's logical plan size estimator is conservative. After a `groupBy`, Spark cannot easily predict how many distinct keys exist without CBO and column statistics. It defaults to assuming the size is as large as the input or a default large value (e.g., `Long.MaxValue`), bypassing the `autoBroadcastJoinThreshold`. (AQE fixes this at runtime).

**36. Scenario:** You query an Iceberg/Delta table: `SELECT * FROM table WHERE ts > '2023-01-01'`. The physical plan shows `PushedFilters: [IsNotNull(ts), GreaterThan(ts, ...)]`.
**Twist:** You change the query to `SELECT * FROM table WHERE cast(ts as date) > '2023-01-01'`. The `PushedFilters` array in the physical plan becomes empty. Why?
**Answer:** Functions applied to the column side of a predicate prevent filter pushdown.
**Mastery Explanation:** The Parquet/ORC reader stores min/max statistics for the raw `ts` column. It does not know the statistics for `cast(ts as date)`. Because the predicate operates on the *result* of the function, Catalyst cannot push this down to the storage layer, forcing Spark to read all data and apply the filter in-memory.

**37. Scenario:** You have a Spark job running with 10 executors, 4 cores each. `spark.default.parallelism` is 40.
**Twist:** You call `df.repartition(10)`. The job becomes much slower, and you see only 10 cores are active. What is the fundamental issue?
**Answer:** You reduced the partition count below the total number of available cores (40), leading to cluster under-utilization.
**Mastery Explanation:** A Spark task operates on exactly one partition. If you have 10 partitions, only 10 tasks can run concurrently. Even though you have 40 cores available, 30 cores will sit idle while the 10 cores grind through larger chunks of data.

**38. Scenario:** A query `SELECT a, max(b) FROM tbl GROUP BY a` generates a `HashAggregate` plan.
**Twist:** You change it to `SELECT a, collect_list(b) FROM tbl GROUP BY a`. The physical plan changes to `SortAggregate`. Why?
**Answer:** `collect_list` creates complex structures that might not be supported efficiently by Tungsten's `HashAggregate` fast map, or string/array accumulation exceeds the mutable state constraints of HashAggregate.
**Mastery Explanation:** HashAggregate requires the aggregation buffer to use mutable primitive types (Tungsten row format). `collect_list` builds dynamic arrays, which rely on arbitrary object allocation. If Spark determines the buffer object cannot be backed by Tungsten, it falls back to `ObjectHashAggregate` or `SortAggregate`, which are much slower.

**39. Scenario:** You read data: `df = spark.read.parquet("...")`. You count it, it yields 1,000,000 rows.
**Twist:** You use `df.sample(withReplacement=False, fraction=1.0).count()`. It yields 998,542 rows. Why didn't it return exactly 1,000,000?
**Answer:** The `fraction` in `sample` is a probability, not a hard guaranteed percentage.
**Mastery Explanation:** Spark's `sample` uses a Bernoulli trial for each row (if `withReplacement=False`). It generates a random number per row and keeps it if it's $< 1.0$. Due to the nature of floating-point math and random number generators, the exact count will fluctuate around the expected value.

**40. Scenario:** You are querying a highly nested JSON dataset using Parquet. `df.select("payload.user.address.city")`.
**Twist:** You change the source format from Parquet to raw JSON files. The query execution time increases by 10x. Why?
**Answer:** Parquet supports columnar projection; JSON requires full row parsing.
**Mastery Explanation:** In Parquet, `payload.user.address.city` is stored as a distinct physical column path. Spark only reads those specific bytes from disk. In JSON, Spark must read the entire line, parse the entire complex JSON string into memory, and then extract the nested field, wasting massive I/O and CPU.

## 4. Coding & Debugging Questions (10 Questions)

**41. The OOM on Driver:**
```python
# Code runs on a 4GB Driver, 16GB Executors
df = spark.read.parquet("s3://huge_table_1TB")
results = df.groupBy("category").count().collect()
```
**Issue:** The job crashes with `java.lang.OutOfMemoryError` on the Driver.
**Diagnosis:** The user called `.collect()`, which sends all aggregated results back to the driver memory. Even though it's an aggregation, if there are tens of millions of distinct `category` values, the resulting array exceeds the driver's 4GB heap.
**Fix:** Write the results to distributed storage instead of collecting: `df.groupBy("category").count().write.parquet("s3://...")`, or increase Driver memory if absolute necessary.

**42. The Missing Broadcast:**
```python
small_df = spark.table("config").filter("active = true") # ~1MB
large_df = spark.table("transactions") # ~100TB
res = large_df.join(small_df, "store_id")
```
**Issue:** Looking at the Spark UI, it executes a `SortMergeJoin` and takes hours.
**Diagnosis:** The CBO size estimator couldn't guarantee the size of `small_df` after the `filter` operation. It fell back to the default size estimate (often `Long.MaxValue`), thus skipping the broadcast.
**Fix:** Force the broadcast using a hint: `large_df.join(broadcast(small_df), "store_id")`.

**43. The Exploding Cartesian:**
```python
df1 = spark.range(1000)
df2 = spark.range(1000)
res = df1.join(df2).filter(df1.id == df2.id)
```
**Issue:** The query takes surprisingly long for just 1,000 rows.
**Diagnosis:** The user wrote an implicit cross join followed by a filter, rather than supplying the join condition directly to the `join` method. Catalyst might fail to optimize this `Filter(CrossJoin)` into an `InnerJoin` depending on version/config, resulting in a $1000 \times 1000 = 1,000,000$ row Cartesian product before filtering.
**Fix:** Provide the condition in the join: `df1.join(df2, df1.id == df2.id, "inner")`.

**44. The Skewed GroupBy:**
```python
df = spark.read.parquet("...")
df.groupBy("customer_id").agg(countDistinct("session_id")).write...
```
**Issue:** One task out of 200 is taking 45 minutes, while others take 10 seconds.
**Diagnosis:** The data is skewed on `customer_id` (e.g., a null customer, or a super-user). `countDistinct` is particularly vulnerable because it requires all records for a key to reach a single executor to evaluate distinctness, severely limiting partial aggregation benefits.
**Fix:** Add a salting mechanism (e.g., `concat("customer_id", rand())`), aggregate partially, then aggregate again on the original key, OR enable AQE skew optimization if applicable.

**45. The Cache Invalidation Trap:**
```python
df = spark.read.csv("data.csv")
df.cache()
df.count() # Materializes cache
spark.catalog.refreshByPath("data.csv")
res = df.filter("val > 10").count()
```
**Issue:** The second count takes just as long as the first, ignoring the cache.
**Diagnosis:** Calling `spark.catalog.refreshByPath` or `refreshTable` forcefully invalidates the cache for any dataframes referencing that underlying data. Spark dumps the cached blocks and physically re-reads the CSV from disk for the second action.
**Fix:** Remove the refresh call if the data hasn't actually changed on disk, or accept the recalculation penalty.

**46. UDF Performance Killer:**
```python
def classify(val):
    return "high" if val > 100 else "low"
spark.udf.register("classify_udf", classify)
spark.sql("SELECT classify_udf(amount) FROM sales")
```
**Issue:** CPU utilization is extremely high, but throughput is terrible.
**Diagnosis:** This is a Python UDF. It forces Row serialization and IPC to Python workers for every single row, breaking Catalyst vectorization.
**Fix:** Rewrite using native Catalyst expressions: `expr("CASE WHEN amount > 100 THEN 'high' ELSE 'low' END")`. Native functions run in Tungsten and are JIT compiled.

**47. The Small File Writer:**
```python
# df has 10,000 partitions
df.write.parquet("s3://output_path/")
```
**Issue:** The write operation is slow, and subsequent reads are agonizingly slow.
**Diagnosis:** Spark writes one file per task/partition. 10,000 partitions result in 10,000 tiny Parquet files. This thrashes the S3 metadata API and ruins Parquet block compression.
**Fix:** Coalesce before writing to reduce file count: `df.coalesce(100).write.parquet(...)`.

**48. The Silent Data Loss (Outer Join Nulls):**
```python
left = spark.createDataFrame([(1, "A")], ["id", "val"])
right = spark.createDataFrame([(2, "B")], ["id", "val"])
res = left.join(right, "id", "left").filter(col("right.val") != "B")
```
**Issue:** `res` returns 0 rows, but the user expects the left row `(1, "A")` to be retained.
**Diagnosis:** The `LEFT JOIN` produces `(1, "A", NULL, NULL)`. The `.filter(col("right.val") != "B")` evaluates `NULL != "B"`, which evaluates to `NULL` (False). The row is dropped.
**Fix:** Account for nulls generated by outer joins: `.filter(col("right.val").isNull() | (col("right.val") != "B"))`.

**49. The Sort Merge Memory Spill:**
```python
spark.conf.set("spark.sql.shuffle.partitions", "2")
df1.join(df2, "key").write...
```
**Issue:** Both DataFrames are 100GB. The Spark UI shows massive "Spill (Memory)" and "Spill (Disk)".
**Diagnosis:** By setting shuffle partitions to 2, you are forcing 100GB of data to be sorted and merged by only 2 tasks. Each task gets 50GB. This completely overflows the executor memory buffer, forcing Spark to constantly serialize and write chunks to local disk (spilling) during the sort phase.
**Fix:** Increase shuffle partitions significantly (e.g., 200, 1000, or let AQE manage it) to reduce the data-per-task ratio: `spark.conf.set("spark.sql.shuffle.partitions", "2000")`.

**50. Unnecessary Window Shuffle:**
```python
from pyspark.sql.window import Window
w = Window.partitionBy("user_id").orderBy("timestamp")
df.withColumn("prev", lag("event").over(w))\
  .withColumn("next", lead("event").over(w))
```
**Issue:** The physical plan shows two separate `Exchange` (shuffle) and `Sort` operations.
**Diagnosis:** Although the Window specification is mathematically identical, Spark sometimes struggles to reuse the Exchange/Sort if the window definitions aren't explicitly shared or if intermediate projections break the pipeline. (Note: Modern Catalyst is better at this, but it can still happen with complex nested logic).
**Fix:** Ensure the exact same `w` object is passed, and avoid interrupting the pipeline with operations that might force a new stage. If needed, manually `repartition("user_id").sortWithinPartitions("user_id", "timestamp")` before applying the windows to force a single exchange.
