# Elite Technical Assessment: Spark Shell

## Part 1: True/False Questions (10 Questions)

1. **Question:** The Spark Shell circumvents the need for a Driver JVM by compiling bytecode directly on the executor nodes.
   **Answer:** False
   **Mastery Explanation:** The Spark Shell relies on the Driver JVM to run the REPL and dynamically compile code. Executors only deserialize and run the bytecode, they do not compile it.

2. **Question:** Spark's Closure Cleaner is responsible for serializing datasets using Kryo before sending them to executors.
   **Answer:** False
   **Mastery Explanation:** The Closure Cleaner recursively inspects closures (functions) via Java reflection to isolate and prune unneeded outer-scope references, preventing massive object serialization. It does not serialize datasets.

3. **Question:** The REPL Class Server is an HTTP/RPC mechanism that serves dynamically generated bytecode from the Driver to Executor nodes.
   **Answer:** True
   **Mastery Explanation:** Executors need the synthetic classes generated by the Driver's REPL. The REPL Class Server distributes this bytecode over the network so worker classloaders can resolve it.

4. **Question:** Tungsten Whole-Stage Code Generation (WSCG) writes low-level Java code to process data in CPU registers and L1/L2 caches, bypassing the JVM garbage collector for intermediate records.
   **Answer:** True
   **Mastery Explanation:** WSCG collapses the physical execution plan into a single optimized Java function, avoiding virtual function calls and the Volcano Iterator model, heavily relying on off-heap memory.

5. **Question:** Calling `.collect()` on a distributed dataset evenly partitions the output data across all executors to avoid Out-Of-Memory errors.
   **Answer:** False
   **Mastery Explanation:** `.collect()` funnels all data from the executors directly into the Driver JVM's heap memory. If the data exceeds the Driver's memory allocation, it causes a catastrophic `java.lang.OutOfMemoryError`.

6. **Question:** Declaring a custom class at the root of the Spark Shell REPL makes it inherently serializable because the REPL is a single-node local environment.
   **Answer:** False
   **Mastery Explanation:** The REPL wraps every variable in a synthetic outer object. If you reference it in a distributed closure, Spark attempts to serialize the entire REPL line object, often leading to `TaskNotSerializableException`.

7. **Question:** Using the `explain("codegen")` function allows developers to inspect the low-level Java code that Tungsten generates.
   **Answer:** True
   **Mastery Explanation:** `explain("codegen")` reveals the physical plan and the actual Java source code generated by Tungsten, proving whether multiple operators were successfully collapsed into a single loop.

8. **Question:** Using `sc.setLocalProperty("spark.scheduler.pool", "pool_name")` in the Spark Shell assigns subsequent Spark jobs to a specific Fair Scheduler pool across the cluster.
   **Answer:** True
   **Mastery Explanation:** This thread-local property allows the DAGScheduler to route interactive jobs to specific resource pools, preventing heavy ad-hoc queries from blocking other interactive commands.

9. **Question:** The `spark.catalog.dropTempView()` method drops the table's metadata and deletes the underlying data from distributed storage.
   **Answer:** False
   **Mastery Explanation:** The Catalog API manages metadata and session memory references. Dropping a temp view only removes the Metastore/session reference, leaving the underlying data intact.

10. **Question:** When Tungsten Whole-Stage CodeGen breaks or is disabled, Spark falls back to the Volcano Iterator model.
    **Answer:** True
    **Mastery Explanation:** Without WSCG, Spark uses the Volcano Iterator model, where each operator calls `next()` on its child, causing massive CPU cache misses and virtual function call overhead.

## Part 2: Multiple Choice Questions (15 Questions)

11. **Question:** Which component on the executor side loads the dynamically generated bytecode sent by the Driver?
    - A) Catalyst Optimizer
    - B) DAGScheduler
    - C) REPL Class Server (ClassLoader)
    - D) Tungsten Engine
    **Answer:** C
    **Mastery Explanation:** The custom REPL ClassLoader resolves and loads the synthetic classes deserialized on the executor, originally served by the REPL Class Server on the Driver.

12. **Question:** What is the primary cause of a `TaskNotSerializable` exception in the Spark Shell?
    - A) Using Parquet instead of ORC
    - B) Referencing a globally scoped REPL variable inside a distributed closure
    - C) Running out of Driver heap memory
    - D) Tungsten CodeGen failing
    **Answer:** B
    **Mastery Explanation:** The REPL wraps global variables in hidden objects. Referencing them forces the Closure Cleaner to serialize the entire REPL outer class, which is usually not serializable.

13. **Question:** Which operation scans only the first few partitions sequentially until a limit is reached, instead of computing the entire DAG?
    - A) `.collect()`
    - B) `.toPandas()`
    - C) `.take(k)`
    - D) `.count()`
    **Answer:** C
    **Mastery Explanation:** `.take(k)` allows Catalyst to optimize the job by scanning partitions one by one until exactly `k` rows are found, avoiding a full cluster execution.

14. **Question:** In an `explain()` physical plan, what character indicates that an operator is utilizing Tungsten Whole-Stage Code Generation?
    - A) `+`
    - B) `*`
    - C) `#`
    - D) `@`
    **Answer:** B
    **Mastery Explanation:** The `*` prefix before an operator in the physical plan signifies that it is part of a WholeStageCodegen subplan.

15. **Question:** How does the Closure Cleaner interact with the Abstract Syntax Tree (AST)?
    - A) It translates the AST into Tungsten Java code.
    - B) It traverses the AST via Java reflection to isolate exact variable dependencies.
    - C) It compiles the AST into Scala bytecode.
    - D) It serializes the AST to send to Executors.
    **Answer:** B
    **Mastery Explanation:** The Closure Cleaner inspects the AST to find precisely which outer variables a function uses, pruning unneeded references to prevent large object serialization.

16. **Question:** What happens when you invoke `.collect()` on a dataset that is 5 times larger than the Driver's memory?
    - A) The executors automatically spill the data to disk.
    - B) The Driver JVM enters a garbage collection spiral and crashes with `OutOfMemoryError`.
    - C) The DAGScheduler cancels the job automatically.
    - D) Tungsten compresses the data in L1 cache.
    **Answer:** B
    **Mastery Explanation:** `.collect()` sends all data directly to the Driver heap. If the dataset exceeds heap capacity, it crashes the Driver and destroys the REPL session state.

17. **Question:** Which API allows dynamic, programmatic inspection of cached tables and temporary views in the Spark Shell?
    - A) `spark.sql`
    - B) `spark.catalog`
    - C) `sc.getConf`
    - D) `spark.memory`
    **Answer:** B
    **Mastery Explanation:** The `spark.catalog` API (e.g., `listTables`, `isCached`, `dropTempView`) allows advanced engineers to manage metastore references programmatically.

18. **Question:** How does Spark Shell route concurrent queries to prevent head-of-line blocking?
    - A) Using YARN dynamically.
    - B) Using `sc.setJobGroup` with interrupt capabilities.
    - C) Using `sc.setLocalProperty("spark.scheduler.pool", ...)` to leverage the Fair Scheduler.
    - D) Using multiple SparkContexts in one shell.
    **Answer:** C
    **Mastery Explanation:** Setting the thread-local property `spark.scheduler.pool` routes the specific job to a Fair Scheduler pool, allowing concurrent queries without blocking.

19. **Question:** Which compiler does the Spark Driver extend to create its REPL?
    - A) `javac`
    - B) `scala.tools.nsc.interpreter.ILoop`
    - C) `org.apache.spark.Compiler`
    - D) `KryoCompiler`
    **Answer:** B
    **Mastery Explanation:** Spark extends the standard Scala interpreter (`ILoop`) to intercept inputs, compile them on the fly, and manage session state.

20. **Question:** What serialization framework is typically used for distributed closures in Spark?
    - A) Kryo Serialization
    - B) Java Serialization
    - C) Protobuf
    - D) Avro
    **Answer:** B
    **Mastery Explanation:** While Kryo is often used for data, closures (the actual bytecode and captured variables of functions) are typically serialized using Java's built-in serialization.

21. **Question:** What does WSCG stand for in the context of Tungsten?
    - A) Wide-Shuffle Computation Graph
    - B) Whole-Stage Code Generation
    - C) Worker-Side Class Generation
    - D) Window-Sorted Cache Grouping
    **Answer:** B
    **Mastery Explanation:** Whole-Stage Code Generation collapses multiple physical plan operators into a single optimized Java function to maximize CPU efficiency.

22. **Question:** What is the fundamental anti-pattern that leads to `TaskNotSerializable` in a REPL?
    - A) Not importing `org.apache.spark.sql.functions._`
    - B) Referencing globally scoped REPL variables inside distributed map/filter functions.
    - C) Using DataFrames instead of RDDs.
    - D) Setting the driver memory too high.
    **Answer:** B
    **Mastery Explanation:** The hidden synthetic classes created by the REPL are generally not serializable. Referencing them forces Spark to attempt to serialize them, resulting in failure.

23. **Question:** What command programmatically kills a runaway REPL query assigned to a specific group?
    - A) `sc.killTask(taskId)`
    - B) `sc.cancelJobGroup("group_id")`
    - C) `spark.stop()`
    - D) `catalog.clearCache()`
    **Answer:** B
    **Mastery Explanation:** By assigning a job group via `sc.setJobGroup()`, you can gracefully kill all jobs in that group using `cancelJobGroup()` without terminating the entire JVM.

24. **Question:** Why does Spark Shell have high startup latency (10-30s)?
    - A) It has to read data from HDFS before booting.
    - B) It compiles the entire Spark source code on boot.
    - C) The JVM boots, Netty binds, and RPC endpoints spin up to connect to the cluster.
    - D) It runs a garbage collection cycle immediately.
    **Answer:** C
    **Mastery Explanation:** The Spark Shell instantly acts as a distributed driver, meaning it must instantiate network interfaces, bind RPC endpoints, and negotiate with the cluster manager on startup.

25. **Question:** Which phase builds the final execution DAG before bytecode is sent to Executors?
    - A) Catalyst Physical Planning
    - B) Tungsten Evaluation
    - C) Closure Cleaning
    - D) YARN Scheduling
    **Answer:** A
    **Mastery Explanation:** Catalyst's physical planning determines the exact execution strategy (the DAG), after which the Closure Cleaner preps the functions for network transmission.

## Part 3: Small Twist Questions (15 Questions)

26. **Scenario:** You run a query with `.collect()` and it crashes the Driver.
    **Twist:** You change it to `.take(100)`. Does it still crash if the total dataset is 50TB?
    **Answer:** No.
    **Mastery Explanation:** `.take()` optimizes the execution by only pulling enough partitions to satisfy the 100-row limit, safely bringing a tiny amount of data to the Driver.

27. **Scenario:** You define `val threshold = db.getThreshold()` in the REPL and use `threshold` in a filter. It works fine.
    **Twist:** You define `val conf = new DBConf()` and use `conf.getThreshold()` inside the filter. What happens?
    **Answer:** It fails with `TaskNotSerializable`.
    **Mastery Explanation:** `threshold` is evaluated on the driver as a primitive, which is serializable. `conf` is a complex object tied to the REPL wrapper, and invoking a method on it inside the closure forces serialization of the wrapper.

28. **Scenario:** You check an `explain()` plan and see `*(1) Project`.
    **Twist:** You disable `spark.sql.codegen.wholeStage`. What prefix do you see now?
    **Answer:** No `*` prefix.
    **Mastery Explanation:** Without Whole-Stage CodeGen, operators fall back to Volcano Iterator and lose the `*` designation in the physical plan.

29. **Scenario:** You drop a temp view using `catalog.dropTempView("view_name")`. The view is removed from memory.
    **Twist:** The view was created from a Parquet file via `.createOrReplaceTempView()`. Is the Parquet file deleted?
    **Answer:** No.
    **Mastery Explanation:** Temp views are purely logical/metadata constructs tied to the SparkSession. Dropping them does not issue filesystem deletes.

30. **Scenario:** You run `df.count()` and it takes 5 minutes.
    **Twist:** You wrap it in a Scala `Future` and run another `df2.count()` immediately after. By default, do they run completely in parallel?
    **Answer:** Usually no, because they queue in the default FIFO scheduler pool.
    **Mastery Explanation:** Unless you set `spark.scheduler.pool` to use the Fair Scheduler and assign them to different pools, the second job may be blocked by the first job's tasks if the cluster is fully utilized.

31. **Scenario:** You broadcast a 50MB map in the Spark Shell. Executors receive it once.
    **Twist:** You reference a 50MB local REPL variable directly in a UDF instead of broadcasting it. How is network I/O affected?
    **Answer:** The variable is serialized and sent with *every single task*, causing massive network I/O spikes.
    **Mastery Explanation:** Broadcast variables are sent via a BitTorrent-like protocol once per executor. Direct closure references are bundled into the task payload, multiplying the network traffic by the number of tasks.

32. **Scenario:** You start Spark Shell and execute `spark.range(10).show()`. It succeeds.
    **Twist:** You type `class NonSer; val x = new NonSer(); spark.range(10).map(_ => x).show()`. What is the result?
    **Answer:** `TaskNotSerializableException`.
    **Mastery Explanation:** Even though `spark.range` is trivial, mapping over it and referencing an unserializable REPL object causes the closure cleaner to fail during task serialization.

33. **Scenario:** Your physical plan shows `*(1) Filter`.
    **Twist:** You add a highly complex, non-codegen-supported UDF to the filter. Does it retain the `*` prefix?
    **Answer:** No, or it splits into multiple subplans.
    **Mastery Explanation:** If a step cannot be code-generated (like a complex opaque UDF), Tungsten cannot collapse it, breaking the Whole-Stage CodeGen pipeline and reverting that step to Volcano Iterator.

34. **Scenario:** You run `.collect()` on a DataFrame with 10 rows. It succeeds.
    **Twist:** You run `.toPandas()` on a DataFrame with 10 billion rows in PySpark Shell. What happens?
    **Answer:** Driver OOM.
    **Mastery Explanation:** `.toPandas()` behaves identically to `.collect()` in that it pulls all distributed data into the Driver's memory (and specifically, into a local Pandas DataFrame), causing fatal heap exhaustion.

35. **Scenario:** You assign `sc.setJobGroup("G1", "Test")` and run a query.
    **Twist:** You open a new terminal, launch a second Spark Shell, and run `sc.cancelJobGroup("G1")`. Does it kill the first query?
    **Answer:** No.
    **Mastery Explanation:** `sc` (SparkContext) is bound to a single Driver JVM. A second Spark Shell is an entirely separate Driver application; it cannot cancel jobs in the first shell's context.

36. **Scenario:** The Closure Cleaner successfully prunes unused variables.
    **Twist:** A variable is referenced inside an `if(false)` block in your distributed closure. Does the Closure Cleaner prune it?
    **Answer:** No, it must serialize it.
    **Mastery Explanation:** The Closure Cleaner analyzes the AST statically via reflection. It cannot evaluate runtime logic like `if(false)`, so it conservatively captures the variable, potentially causing serialization errors.

37. **Scenario:** You allocate 4GB to executor memory and 1GB to driver memory.
    **Twist:** You reverse it: 1GB to executor, 4GB to driver. You run `.take(1000)`. Does it succeed?
    **Answer:** Yes.
    **Mastery Explanation:** `.take()` pulls minimal data. While executors have less memory, processing 1000 rows is trivial. The large driver memory is unutilized but doesn't cause failure here.

38. **Scenario:** You launch Spark Shell locally with `local[*]`.
    **Twist:** You launch it on YARN with `--deploy-mode cluster`. What happens?
    **Answer:** It fails or is unsupported.
    **Mastery Explanation:** The Spark Shell requires interactivity. It must run in `client` mode so the REPL prompt is attached to your local terminal. Cluster mode detaches the driver to a remote node.

39. **Scenario:** You write `spark.catalog.clearCache()`. Data in memory is evicted.
    **Twist:** You immediately run an action on a DataFrame that was cached. Does it fail?
    **Answer:** No.
    **Mastery Explanation:** Spark's cache is fault-tolerant. If the cached data is evicted, Spark simply recomputes the data from the original lineage (DAG) on the next action.

40. **Scenario:** Tungsten generates Java bytecode dynamically.
    **Twist:** Your executors are running a different minor version of Java than the Driver. Does Tungsten fail?
    **Answer:** Potentially yes, or it causes severe runtime exceptions.
    **Mastery Explanation:** If the bytecode generated on the Driver is incompatible with the Executor JVMs, the custom ClassLoader will fail to resolve or execute the classes. JVM consistency is critical.

## Part 4: Coding & Debugging Questions (10 Questions)

41. **Debugging:** 
    ```scala
    class Config { val max = 100 }
    val conf = new Config()
    spark.range(1000).filter(r => r.getLong(0) > conf.max).show()
    ```
    *Error:* TaskNotSerializable. 
    **Fix:** 
    **Mastery Explanation:** Extract the primitive before the closure.
    ```scala
    val localMax = conf.max
    spark.range(1000).filter(r => r.getLong(0) > localMax).show()
    ```

42. **Debugging:**
    You want to see the underlying Java code Spark generated for your DataFrame `df`.
    *Code:* `df.explain()`
    *Result:* Only the logical and physical plan is shown.
    **Fix:**
    **Mastery Explanation:** Change to `df.explain("codegen")` to force Catalyst to output Tungsten's dynamically generated Whole-Stage Java code.

43. **Debugging:**
    A background job in the shell is locking up your terminal.
    *Code:* 
    ```scala
    sc.setJobGroup("heavy", "Heavy Job")
    heavyDF.write.parquet("/out")
    ```
    You can't type anything.
    **Fix:**
    **Mastery Explanation:** You must run the heavy job asynchronously using a Scala `Future`, allowing the REPL thread to remain responsive.

44. **Debugging:**
    You want to ensure two asynchronous jobs in the REPL share cluster resources evenly instead of blocking each other.
    *Code:* (No specific properties set)
    **Fix:**
    **Mastery Explanation:** Enable Fair Scheduler and set pool properties before launching: `sc.setLocalProperty("spark.scheduler.pool", "poolA")`.

45. **Debugging:**
    You need to drop all temporary views containing "temp" to free up Driver memory, but doing it manually is too slow.
    *Code:* `spark.sql("DROP VIEW ...")` (Repeatedly)
    **Fix:**
    **Mastery Explanation:** Use the Catalog API:
    ```scala
    spark.catalog.listTables().filter(_.name.contains("temp")).foreach(t => spark.catalog.dropTempView(t.name))
    ```

46. **Debugging:**
    *Code:* `val data = spark.read.parquet("s3://huge-bucket/"); data.collect()`
    *Error:* `java.lang.OutOfMemoryError: Java heap space` on Driver.
    **Fix:**
    **Mastery Explanation:** Never use `.collect()` on massive datasets. Use `data.show()`, `data.take(20)`, or write the output directly to storage (`data.write.parquet(...)`).

47. **Debugging:**
    ```scala
    object Helpers { def calc(i: Long) = i * 2 }
    spark.range(10).map(r => Helpers.calc(r)).show()
    ```
    This works locally but sometimes fails in distributed mode if `Helpers` relies on outer REPL state.
    **Fix:**
    **Mastery Explanation:** Define the function natively as a Spark UDF or place the logic entirely inside the `.map()` closure to avoid external object dependencies.

48. **Debugging:**
    Your Spark Shell feels extremely slow after 2 hours of running 500 different queries and creating 100 cached DataFrames.
    *Code:* You keep creating new `cache()` calls.
    **Fix:**
    **Mastery Explanation:** The memory is full, and GC overhead is high. Run `spark.catalog.clearCache()` to evict all cached data and free up the BlockManager.

49. **Debugging:**
    You want to check if a specific table `my_cache_tb` is currently cached in memory using the shell.
    *Code:* `spark.sql("SHOW TABLES")` doesn't tell you if it's cached.
    **Fix:**
    **Mastery Explanation:** Use `spark.catalog.isCached("my_cache_tb")` which returns a boolean indicating its cache status.

50. **Debugging:**
    You run `df.explain()` and notice the `*` prefix is missing across your entire plan.
    *Code:* `df = df.withColumn("new", complexUDF($"col"))`
    **Fix:**
    **Mastery Explanation:** The `complexUDF` broke Whole-Stage CodeGen. To restore performance, replace the opaque UDF with native Spark SQL functions (e.g., `when().otherwise()`), which Tungsten can compile into Java bytecode.
