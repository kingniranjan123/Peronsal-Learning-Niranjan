# Websockets in Apache Spark - Elite Assessment

## Part 1: True/False Questions

**1. Connecting WebSockets directly to Spark Executors is considered a highly scalable, production-grade enterprise pattern.**
*   **Answer:** False
*   **Mastery Explanation:** Direct connection is an anti-pattern due to elasticity and fault-tolerance issues. In enterprise architectures, a lightweight proxy (like Node.js or Go) should bridge WebSockets to Kafka, which Spark then consumes.

**2. Catalyst optimizer cannot push down filters to a raw continuous TCP stream prior to ingestion.**
*   **Answer:** True
*   **Mastery Explanation:** The Catalyst optimizer operates on Spark SQL abstractions (like DataFrames/Datasets). A raw TCP stream lacks the schema and structured format required for Catalyst to push down filters; filtering must occur post-ingestion.

**3. When ingesting high-frequency WebSocket data, converting raw byte arrays directly to Java Strings is the recommended approach to minimize memory overhead.**
*   **Answer:** False
*   **Mastery Explanation:** Standard Java string deserialization becomes a massive bottleneck due to object churn and GC pressure. The optimal strategy is a two-stage ingestion where byte arrays are directly copied to an off-heap buffer managed by Tungsten.

**4. Setting `spark.streaming.receiver.maxRate` helps enforce backpressure and prevent Executor OutOfMemory (OOM) errors during bursty WebSocket traffic.**
*   **Answer:** True
*   **Mastery Explanation:** Without backpressure, high-throughput bursts overwhelm the BlockManager. Enforcing a max rate allows standard TCP sliding windows to signal the sender, preventing fatal OOMs.

**5. Tungsten's `UnsafeRow` binary format relies heavily on standard JVM Garbage Collection to manage its memory lifecycle.**
*   **Answer:** False
*   **Mastery Explanation:** Tungsten is specifically designed to operate on off-heap memory, bypassing the JVM's Garbage Collector. This drastically reduces GC pauses that would otherwise obliterate latency SLAs.

**6. When implementing a custom DStream Receiver in Scala for WebSockets, using `StorageLevel.MEMORY_AND_DISK_2` is recommended to handle sudden bursts.**
*   **Answer:** True
*   **Mastery Explanation:** Replicating blocks across two nodes (`_2`) provides fault tolerance against node failures, and allowing spill to disk prevents OOMs during severe market volatility spikes or sudden bursts.

**7. Event-time watermarking ensures that intermediate state is kept indefinitely in case of extremely late WebSocket packets.**
*   **Answer:** False
*   **Mastery Explanation:** Watermarking is designed to purge state after a specified threshold passes. Keeping state indefinitely would lead to memory leaks in the Executor.

**8. Whole-Stage CodeGen generated by the Catalyst Optimizer traverses standard Java object graphs to apply schema validations.**
*   **Answer:** False
*   **Mastery Explanation:** Whole-Stage CodeGen compiles operations into highly optimized JVM bytecode that reads directly from the byte array/off-heap memory, applying filters in CPU registers and explicitly *bypassing* object graph traversal.

**9. In a custom WebSocket sink, it is best practice to collect all data to the Driver node before broadcasting to the WebSocket clients.**
*   **Answer:** False
*   **Mastery Explanation:** Collecting data to the Driver bottleneck paralyzes the node and limits scalability. The correct approach uses `foreachPartition` to distribute network egress directly from the Executors.

**10. Configuring G1GC or ZGC is critical for WebSocket ingestion to prevent long GC pauses from terminating TCP heartbeats.**
*   **Answer:** True
*   **Mastery Explanation:** WebSockets rely on TCP heartbeats to maintain the connection. Long GC pauses (Stop-The-World) can cause heartbeat timeouts, leading to abrupt and unwanted connection terminations.

## Part 2: Multiple Choice Questions

**11. Why is the architectural mismatch between Apache Spark and WebSockets so profound?**
*   A) Spark uses UDP while WebSockets require TCP.
*   B) Spark operates on distributed partitions and task-based execution, whereas WebSockets are long-lived, point-to-point TCP connections.
*   C) WebSockets cannot transmit binary data, which Spark requires.
*   D) Spark's Driver node cannot establish network connections.
*   **Answer:** B
*   **Mastery Explanation:** Spark is designed for distributed, parallel processing of finite data chunks (partitions). A WebSocket is a stateful, continuous, single point-to-point connection, creating a fundamental mismatch in how work is distributed and managed.

**12. When processing millions of small JSON payloads from a WebSocket, what is the primary cause of latency SLA breaches in a default Spark configuration?**
*   A) Network bandwidth saturation
*   B) Disk I/O bottlenecks in the BlockManager
*   C) JVM Garbage Collection (GC) pauses caused by massive object churn during deserialization
*   D) Catalyst Optimizer compilation time
*   **Answer:** C
*   **Mastery Explanation:** Deserializing millions of small JSON payloads into standard Java objects creates massive object churn on the heap, leading to frequent and lengthy Stop-The-World GC pauses that destroy sub-second latency SLAs.

**13. What is the role of the Catalyst Optimizer when reading a buffered WebSocket stream from Kafka using a predefined `StructType`?**
*   A) It automatically establishes the WebSocket connection to the original source.
*   B) It generates highly optimized JVM bytecode (Whole-Stage CodeGen) to process the stream directly in Tungsten's off-heap memory.
*   C) It automatically tunes the JVM garbage collector based on stream velocity.
*   D) It distributes the Kafka partitions dynamically based on CPU load.
*   **Answer:** B
*   **Mastery Explanation:** By providing a schema, Catalyst can use Whole-Stage CodeGen to compile the deserialization, casting, and filtering into a single function that operates directly on Tungsten's binary `UnsafeRow` format, bypassing intermediate object creation.

**14. In Spark Structured Streaming, how does a watermark prevent memory leaks when processing chaotic, out-of-order WebSocket data?**
*   A) It immediately drops any data that arrives out of order.
*   B) It writes all late data directly to HDFS without processing.
*   C) It instructs the state store to maintain intermediate aggregations only up to a specified event-time delay, purging older state.
*   D) It increases the JVM heap size dynamically.
*   **Answer:** C
*   **Mastery Explanation:** A watermark defines a threshold for late data. Once the event-time watermark advances past a certain point, Spark safely purges the corresponding aggregate state from memory/RocksDB, bounding the overall memory footprint.

**15. When outputting data to a WebSocket from Spark, what is the advantage of using `foreachPartition` over `foreach`?**
*   A) `foreachPartition` automatically handles JSON serialization.
*   B) `foreachPartition` establishes one WebSocket connection per row, reducing latency.
*   C) `foreachPartition` allows establishing a single WebSocket connection per partition, amortizing the connection overhead.
*   D) `foreachPartition` executes on the Driver node, ensuring ordered delivery.
*   **Answer:** C
*   **Mastery Explanation:** Connection establishment (TCP handshake) is expensive. `foreachPartition` allows you to open one connection for an entire partition of data, reuse it for all rows in that partition, and then close it, drastically reducing overhead compared to opening a connection per row.

**16. Which memory format does Tungsten use to optimize execution?**
*   A) Standard Java Objects
*   B) Kryo Serialized Objects
*   C) UnsafeRow binary format
*   D) Apache Parquet
*   **Answer:** C
*   **Mastery Explanation:** Tungsten uses the `UnsafeRow` binary format, which stores data off-heap. This allows Spark to perform operations directly on raw memory using CPU registers, avoiding JVM object overhead and GC pressure.

**17. What happens if a WebSocket Receiver in Spark does not enforce backpressure?**
*   A) The Catalyst optimizer crashes.
*   B) The WebSocket connection automatically upgrades to HTTP/2.
*   C) Incoming spikes overwhelm the BlockManager, leading to fatal Executor OutOfMemory (OOM) errors.
*   D) Spark automatically scales up the number of Executors.
*   **Answer:** C
*   **Mastery Explanation:** Without backpressure (like `spark.streaming.receiver.maxRate`), Spark attempts to ingest data as fast as the network allows. During a burst, this rapidly fills Executor memory, leading to OOMs. Backpressure signals the TCP sliding window to slow down the sender.

**18. Why must the WebSocket receiver thread remain non-blocking?**

*   **Answer:** B
*   **Mastery Explanation:** The receiver thread's sole job is pulling data from the network. If it blocks (e.g., waiting for complex processing or synchronous disk writes), the network buffer fills up, packets drop, and the connection may sever. Persistence should be delegated to Spark's async mechanisms.

*   **Mastery Explanation:** Terminating WebSockets on a stateless, lightweight proxy allows easy scaling of connection handling. Pushing events to Kafka decouples ingestion from processing, allowing Spark to restart, scale, or recover from failures without disconnecting the end-user WebSockets.

**21. When reading raw byte arrays from a WebSocket, how does modern Spark avoid object churn?**

**22. Which GC configuration is explicitly recommended for preventing WebSocket TCP heartbeat timeouts in Spark?**

**23. What does `StorageLevel.MEMORY_AND_DISK_2` achieve for a DStream WebSocket receiver?**

**24. Why can't the Catalyst Optimizer push down filters to a raw continuous TCP stream?**

**25. When using `from_json` with a `StructType` in Structured Streaming, what is the impact on the physical plan?**

## Part 3: "Small Twist" Questions

**26. Scenario:** You have a custom Scala WebSocket Receiver using `StorageLevel.MEMORY_ONLY`. During a massive market volatility spike, the streaming job crashes with an OOM.
**Twist:** You change the storage level to `StorageLevel.DISK_ONLY`.
**Question:** What is the new expected behavior during a similar burst?
*   A) The job crashes with a NetworkTimeoutException.
*   B) Latency spikes severely as all incoming packets are written synchronously to the local disk, potentially causing upstream TCP backpressure.
*   C) The job processes data instantly without any disk I/O.
*   D) Spark automatically switches back to MEMORY_ONLY.
*   **Answer:** B
*   **Mastery Explanation:** `DISK_ONLY` forces every incoming message to hit the disk before it's considered "received". Disk I/O is orders of magnitude slower than memory. This will bottleneck the receiver thread, causing the TCP receive buffer to fill up, which triggers TCP backpressure to the sender and destroys latency.

*   **Mastery Explanation:** In streaming aggregations, Spark must retain state to handle late data. Without a watermark, Spark doesn't know when a window is "complete", so it must keep the state for *all* windows indefinitely, inevitably causing an OOM.

## Part 4: Coding & Debugging Questions

**41. Debug this PySpark structured streaming snippet.**
```python
df = spark.readStream.format("kafka").option("subscribe", "ws_events").load()
schema = StructType([StructField("data", StringType())])
parsed = df.select(from_json(col("value"), schema))
```
*   **Defect:** The `value` column from Kafka is binary, but `from_json` expects a string.
*   **Resolution:** Cast the binary value to a string before parsing: `from_json(col("value").cast("string"), schema)`.
*   **Mastery Explanation:** Kafka stores payloads as raw byte arrays. Catalyst's `from_json` function requires a String input to parse correctly. Failing to cast will result in a runtime AnalysisException.

**42. Identify the memory leak in this custom Scala WebSocket Receiver.**
```scala
override def onMessage(message: String): Unit = {
  val complexObject = new HeavyParser().parse(message)
  store(complexObject.toString())
}
```
*   **Defect:** Instantiating a `new HeavyParser()` and complex objects inside the `onMessage` callback for every single event.
*   **Resolution:** Keep `onMessage` as lightweight as possible. `store(message)` directly. Move parsing to Spark transformations (DataFrames) so Catalyst can optimize it.
*   **Mastery Explanation:** The `onMessage` thread is a single network thread. Creating heavy objects here causes massive GC churn and stalls the thread, filling the TCP receive buffer and causing dropped connections. Spark's execution engine is built to handle the parsing efficiently *after* ingestion.

**43. A Spark streaming job outputting to WebSockets crashes with "Task not serializable".**
```python
ws_client = websocket.create_connection("ws://host:8080")
def send_data(row):
    ws_client.send(row.data)
df.rdd.foreach(send_data)
```
*   **Defect:** The `ws_client` is instantiated on the Driver, but `foreach` runs on the Executors. TCP socket connections cannot be serialized and sent over the network.
*   **Resolution:** Move connection establishment inside a `foreachPartition` block so the connection is created locally on the Executor.
*   **Mastery Explanation:** Network connections, file handles, and database connections are bound to the specific machine's OS. They cannot be serialized by Kryo/Java and shipped to worker nodes. They must be instantiated within the closure that executes on the worker.

**44. Review this watermarking logic.**
```python
df.withWatermark("processing_time", "10 minutes").groupBy(window(col("event_time"), "5 mins"))
```
*   **Defect:** The watermark is applied to a different time column (`processing_time`) than the window aggregation (`event_time`).
*   **Resolution:** The watermark must be applied to the same timestamp column used in the window aggregation: `withWatermark("event_time", "10 minutes")`.
*   **Mastery Explanation:** Watermarking tracks the maximum observed *event time* to determine when to purge state. If you watermark on processing time but aggregate on event time, Spark cannot correlate the two, and state will never be purged, leading to an OOM.

**45. Why does this JSON parsing approach destroy Tungsten's efficiency?**
```python
rdd = df.rdd.map(lambda row: json.loads(row.value.decode('utf-8')))
df2 = spark.createDataFrame(rdd)
```
*   **Defect:** Using an RDD `map` with Python's `json.loads` forces data out of Tungsten, serializes it to Python, parses it into a Python dictionary, and then incurs massive overhead to infer a schema and convert it back to a DataFrame.
*   **Resolution:** Use native Catalyst functions: `df.select(from_json(col("value").cast("string"), schema))`.
*   **Mastery Explanation:** RDD operations in PySpark invoke the Python worker via Py4J/sockets. This breaks Whole-Stage CodeGen, forces expensive IPC serialization, and creates massive heap objects, completely negating the benefits of Tungsten off-heap execution.

**46. Debug this `foreachBatch` connection logic.**
```python
def write_batch(df, epoch_id):
    ws = create_connection("ws://dest")
    df.foreach(lambda row: ws.send(row.data))
```
*   **Defect:** `ws` is created on the Driver (inside `write_batch`), but `df.foreach` executes on the Executors. The `ws` object will throw a serialization error.
*   **Resolution:** 
```python
def write_batch(df, epoch_id):
    def send_partition(part):
        ws = create_connection("ws://dest")
        for row in part: ws.send(row.data)
        ws.close()
    df.foreachPartition(send_partition)
```
*   **Mastery Explanation:** The outer function of `foreachBatch` runs on the Driver. Any connection created there cannot be used inside RDD/DataFrame actions that execute on worker nodes. Connections must be localized to the worker closures.

**47. A streaming job consuming Kafka WebSocket events is falling behind. The UI shows processing time > batch interval. You see `spark.sql.shuffle.partitions=200`. The input rate is small, but latency is high.**
*   **Defect:** The default 200 shuffle partitions are excessive for a small stream, causing massive task scheduling overhead (200 tiny tasks per micro-batch).
*   **Resolution:** Reduce `spark.sql.shuffle.partitions` to a smaller number (e.g., 2, 4, or matching the number of Kafka partitions/Executor cores) to reduce task overhead.
*   **Mastery Explanation:** In low-volume, low-latency streaming, task scheduling overhead (driver assigning tasks to executors) dominates processing time. Having 200 partitions for 1MB of data means 200 tasks are created doing almost nothing, destroying latency.

**48. Identify the bottleneck in this aggregation.**
```python
df.groupBy("user_id").agg(collect_list("websocket_event"))
```
*   **Defect:** `collect_list` in an unbounded streaming context without a window or watermark will accumulate an infinitely growing array of events for every user in the state store.
*   **Resolution:** Apply a window and a watermark to bound the state, or use a different aggregation that doesn't store unbounded lists (like `count` or `avg`).
*   **Mastery Explanation:** State stores (like RocksDB) are not meant to store infinite data structures. `collect_list` appends to an array forever. This will quickly bloat the state store, causing disk spills and eventually fatal OOMs.

**49. A custom Scala Receiver occasionally throws `java.lang.InterruptedException` during shutdown.**
```scala
override def onStop(): Unit = { client.close() }
```
*   **Defect:** The `client.close()` might be blocking or taking too long, and Spark forcibly interrupts the receiver thread.
*   **Resolution:** Handle the close gracefully, perhaps in a separate thread, or ensure the WebSocket client implementation supports immediate non-blocking closure. Catch and ignore the interrupt if it's during an intentional shutdown.
*   **Mastery Explanation:** Spark expects `onStop` to return promptly. If the underlying network library attempts a graceful TCP teardown that stalls, Spark's task reaper will interrupt the thread. Graceful teardown logic must be robust to thread interruptions.

**50. You are using `MEMORY_AND_DISK` but still getting OOMs on bursty WebSocket streams before data even processes. Why?**
*   **Defect:** `MEMORY_AND_DISK` dictates how the BlockManager stores *blocks* after the receiver buffers them. However, if the network receive buffer or the intermediate `store()` queue fills up faster than Spark can cut blocks, the JVM heap will OOM before the storage level logic even applies.
*   **Resolution:** Implement strict backpressure (`spark.streaming.receiver.maxRate`), tune the JVM heap, or ideally, move to the Kafka proxy architecture.
*   **Mastery Explanation:** The Receiver architecture has internal queues between the network socket and the BlockManager. If ingestion vastly outpaces block creation, these internal JVM queues explode. Storage levels only protect you *after* blocks are formed; backpressure protects you *before*.
