# 🔥 Master Class: Streaming Performance Tuning

## Overview

Apache Spark Structured Streaming is a fault-tolerant, exactly-once stream processing engine built on top of the Spark SQL execution engine. Unlike the deprecated DStream API, Structured Streaming models an unbounded data stream as a continuously appended, unbounded table — every micro-batch or continuous trigger reads new rows, processes them through the Catalyst optimizer's full pipeline, and commits results atomically via a Write-Ahead Log (WAL) and checkpoint mechanism. This architectural decision means streaming queries inherit the full power of Catalyst predicate pushdown, Tungsten binary format, and Whole-Stage CodeGen — but it also means that the same performance failure modes that plague batch jobs (data skew, excessive shuffle, GC pressure) are amplified in streaming because they repeat on every trigger.

Performance tuning Structured Streaming is fundamentally about controlling throughput, latency, and state growth across three axes simultaneously. An untuned streaming job will eventually exhibit one of three failure modes: **trigger stacking** (a micro-batch takes longer than its trigger interval, causing a perpetual queue backlog), **state store explosion** (stateful aggregations accumulate unbounded state in the executor JVM heap or RocksDB, causing OOM or compaction stalls), or **offset surge** (a source delivers data faster than the job can process it, causing runaway memory consumption in the shuffle service). Mastering streaming performance requires understanding exactly where in the execution pipeline each control knob intervenes — from the `StreamExecution` thread on the driver down to RocksDB block cache tuning on each executor.

The six mechanisms covered in this Master Class — backpressure via `maxOffsetsPerTrigger`, trigger interval selection, RocksDB state store configuration, stateful join watermark tuning, and asynchronous progress tracking — form a complete defensive perimeter. Together they prevent any single dimension of the streaming system from becoming the bottleneck that cascades into a full job failure.

## 🏗️ Architectural Deep Dive

### How It Works Under the Hood

Every Structured Streaming query is managed by a `StreamExecution` instance running on the driver in a dedicated daemon thread. On each trigger, `StreamExecution` calls `MicroBatchExecution.constructNextBatch()`, which contacts each configured source (e.g., `KafkaSource`) to determine the latest available offsets. The gap between the previously committed offset (stored in `<checkpoint>/offsets/`) and the latest available offset defines the **input batch**. If `maxOffsetsPerTrigger` is set, `KafkaMicroBatchReader` truncates the end offset so the batch processes at most N records, regardless of what Kafka has available. This is the primary backpressure lever and it operates before any data is read into executor memory.

Once the offset range is determined, the logical plan is constructed by replacing the streaming source with a bounded `KafkaRDD` for that offset range. The full Catalyst pipeline then executes: Analysis resolves column types and schema, Logical Optimization applies predicate pushdown and filter consolidation, Physical Planning selects join strategies (critical for stream-stream joins), and Tungsten's Whole-Stage CodeGen fuses the generated bytecode into a single `processNext()` loop per stage. For stateful operators — `mapGroupsWithState`, `flatMapGroupsWithState`, `dropDuplicates`, and stream-stream joins — the Physical Plan inserts a `StateStoreSaveExec` node that reads and writes state through the `StateStore` interface, which is backed either by the default HDFS-checkpointed in-memory `HDFSBackedStateStore` or the RocksDB-backed `RocksDBStateStore`.

The RocksDB state store fundamentally changes the memory model for stateful streaming. The default `HDFSBackedStateStore` keeps the entire state snapshot in the executor's JVM heap, which means a 10GB state partition requires 10GB of Java heap per executor — causing catastrophic GC pressure and frequent stop-the-world pauses that can exceed 30 seconds. `RocksDBStateStore` moves state to off-heap native memory and SST files on local disk, with only the RocksDB block cache (`spark.sql.streaming.stateStore.rocksdb.blockCacheSize`, default 8MB — far too small for production) consuming JVM off-heap space. This allows a single executor to manage hundreds of gigabytes of state with sub-millisecond point lookups, because RocksDB uses a Log-Structured Merge (LSM) tree with Bloom filters that bypass disk reads for non-existent keys entirely.

Trigger intervals and the async progress tracking API are the final layer. Setting `Trigger.ProcessingTime("30 seconds")` tells `MicroBatchExecution` to sleep until the interval boundary if the batch completes early, which is essential for cost control in cloud environments where you pay per executor-second. Async progress tracking (`spark.sql.streaming.asyncProgressTrackingEnabled = true`), introduced in Spark 3.5, decouples the WAL commit from the processing loop: the driver commits offsets to the checkpoint store asynchronously in a separate thread while the next batch begins constructing. This alone reduces trigger-to-trigger latency overhead by 15–40% on high-throughput pipelines.

### Key Internal Components

- **`MicroBatchExecution`:** The driver-side orchestrator that drives the trigger loop, constructs the bounded logical plan for each batch, manages the WAL commit sequence, and enforces `maxOffsetsPerTrigger` by negotiating truncated end offsets with each `MicroBatchReader`. It also manages the `epochCoordinator` for continuous processing mode.

- **`KafkaMicroBatchReader`:** The Kafka source's implementation of the `MicroBatchReader` interface. It contacts the Kafka broker metadata endpoint to resolve partition-to-offset mappings, applies `maxOffsetsPerTrigger` per partition proportionally (not globally), and generates a `KafkaRDD` whose partitions map 1-to-1 with Kafka topic partitions, so parallelism is directly determined by Kafka partition count.

- **`RocksDBStateStore`:** An implementation of the `StateStore` trait backed by embedded RocksDB (via JNI). Each state store instance is pinned to a single executor and partition. On trigger commit, it flushes the MemTable to an SST file and uploads a snapshot delta to the checkpoint directory via Hadoop FileSystem, enabling state recovery on executor failure. The LSM compaction background thread competes with task execution for CPU and must be monitored.

- **`WatermarkTracker`:** A driver-side component that aggregates per-partition event-time watermark values reported by each task (via `TaskContext.getLocalProperty`) and advances the global watermark. This global watermark gates state expiry in `mapGroupsWithState` and determines when stream-stream join state buffers can be evicted, making accurate watermark estimation the single most important factor in preventing state unbounded growth.

## ⚠️ Critical Concepts & Common Pitfalls

### Trigger Stacking and the Backpressure Illusion

Structured Streaming has **no built-in backpressure mechanism analogous to Spark Streaming's `spark.streaming.backpressure.enabled`**. If you do not explicitly set `maxOffsetsPerTrigger`, the `KafkaMicroBatchReader` will read every available record up to Kafka's latest offset in a single batch. During a traffic spike — say, a 10x surge from 1M to 10M events per minute — the first over-sized batch will take 10x longer to process, during which Kafka accumulates another 10M records. By the time the second batch starts, consumer lag is 20M records, and the job has entered an unrecoverable death spiral that only a manual offset reset can fix.

The correct approach is to set `maxOffsetsPerTrigger` to the number of records your job can sustainably process in one trigger interval under peak load. If your trigger is 30 seconds and you can process 500K records/trigger under normal conditions, set `maxOffsetsPerTrigger = 300000` to leave a safety margin. This creates a soft ceiling that allows the job to drain accumulated lag gradually during normal periods. Monitor `inputRowsPerSecond` vs `processedRowsPerSecond` in the streaming query progress JSON — when the former exceeds the latter for more than 3 consecutive batches, you have a compounding lag problem.

### RocksDB Compaction and Write Amplification

The most insidious streaming failure in stateful jobs is **RocksDB compaction stalls**. Under high write throughput, RocksDB's LSM compaction background thread falls behind, causing write stalls that block the `StateStoreSaveExec` node — this appears in the Spark UI as an executor task stuck at near-100% duration with no progress. The root cause is almost always insufficient RocksDB write buffer configuration. The default `writeBufferSizeMB = 64MB` and `maxWriteBufferNumber = 2` mean RocksDB stops accepting writes when both 64MB MemTables are full and compaction hasn't caught up. Setting `writeBufferSizeMB = 256` and `maxWriteBufferNumber = 4` increases the in-memory write buffer to 1GB per state partition, providing enough headroom for compaction to catch up during high-ingestion bursts without stalling task execution. Always co-locate RocksDB SST files on NVMe local instance storage, never EBS or network-attached storage, since random read amplification on HDD or high-latency block storage causes 10–100x lookup degradation.

## 📊 Performance Characteristics

| Operation | Complexity | Shuffle? | Notes |
|-----------|-----------|---------|-------|
| Stateless transformation (filter/map) | O(N) per batch | No | Fully pipelined in Tungsten; codegen eliminates virtual dispatch overhead |
| Stateful aggregation (groupBy + watermark) | O(N + S) where S = state size | No | State read/write dominates; RocksDB point lookups are O(log S) with Bloom filter bypass |
| Stream-stream join (with watermark) | O(N × M) worst case per batch | Yes | Both sides buffer in state store; watermark controls eviction and shuffle occurs on join key |
| `flatMapGroupsWithState` | O(N + S) | No | User-defined state; arbitrary logic; no optimizer visibility; must manage expiry manually |
| `dropDuplicates` with watermark | O(N + S) | No | State holds seen keys per watermark window; without watermark, state is unbounded and OOM-certain |
| Kafka offset commit (WAL) | O(P) — P = partition count | No | Driver-side I/O; async tracking removes this from the critical path of next-batch construction |

## 💻 Code Examples

### Example 1: Backpressure via `maxOffsetsPerTrigger` with Lag-Adaptive Throttling

> **What this demonstrates:** How to configure `maxOffsetsPerTrigger` and pair it with a streaming query listener that monitors consumer lag, logging actionable warnings when the job falls behind — revealing the offset negotiation layer that sits above all data reads.

```scala
import org.apache.spark.sql.SparkSession
import org.apache.spark.sql.streaming.{StreamingQuery, StreamingQueryListener, Trigger}
import org.apache.spark.sql.streaming.StreamingQueryListener._
import scala.concurrent.duration._

val spark = SparkSession.builder()
  .appName("BackpressureTuned-KafkaConsumer")
  // Serialize task closures with Kryo, not Java — 3–5x smaller task payloads
  .config("spark.serializer", "org.apache.spark.serializer.KryoSerializer")
  // Async progress tracking: decouple WAL commit from next-batch construction
  .config("spark.sql.streaming.asyncProgressTrackingEnabled", "true")
  // Commit interval for async WAL: write checkpoint every 2 triggers, not every 1
  .config("spark.sql.streaming.asyncProgressTrackingCheckpointIntervalMs", "60000")
  .getOrCreate()

// Register a query listener BEFORE starting the query
// This runs on the driver and receives a StreamingQueryProgress on every batch
spark.streams.addListener(new StreamingQueryListener {
  override def onQueryStarted(event: QueryStartedEvent): Unit = {}
  override def onQueryTerminated(event: QueryTerminatedEvent): Unit = {}

  override def onQueryProgress(event: QueryProgressEvent): Unit = {
    val progress = event.progress
    val inputRate  = progress.inputRowsPerSecond    // rows/sec arriving from source
    val procRate   = progress.processedRowsPerSecond // rows/sec actually processed

    // When input consistently exceeds processing, lag is compounding
    // This is the canary-in-the-coal-mine for trigger stacking
    if (inputRate > procRate * 1.2) {
      println(s"[WARN] LAG COMPOUNDING: input=${inputRate.toLong} rows/s, " +
              s"processed=${procRate.toLong} rows/s — reduce maxOffsetsPerTrigger")
    }

    // Log trigger duration — if this exceeds triggerIntervalMs, we have trigger stacking
    val triggerMs = progress.durationMs.getOrDefault("triggerExecution", 0L)
    println(s"[INFO] Trigger duration: ${triggerMs}ms, " +
            s"numInputRows: ${progress.numInputRows}")
  }
})

val kafkaDF = spark.readStream
  .format("kafka")
  .option("kafka.bootstrap.servers", "broker1:9092,broker2:9092")
  .option("subscribe", "events-topic")
  .option("startingOffsets", "latest")
  // CRITICAL: hard cap on records per trigger — the primary backpressure lever
  // At 30s trigger intervals, 500K rows = ~16K rows/sec processing target
  .option("maxOffsetsPerTrigger", 500000)
  // Fetch up to 64MB from each Kafka partition per poll — reduces round trips
  .option("kafka.max.partition.fetch.bytes", 67108864)
  .load()

import spark.implicits._
val parsed = kafkaDF
  .selectExpr("CAST(key AS STRING)", "CAST(value AS STRING)", "timestamp")
  // Watermark on event time: tolerate up to 10 minutes of late data
  // This also gates state eviction in any downstream stateful operator
  .withWatermark("timestamp", "10 minutes")

val query: StreamingQuery = parsed.writeStream
  .format("delta")
  .option("checkpointLocation", "s3://my-bucket/checkpoints/events")
  // ProcessingTime trigger: batch runs every 30s; if batch finishes early, Spark sleeps
  // This prevents hot-loops and reduces cloud executor costs significantly
  .trigger(Trigger.ProcessingTime(30.seconds))
  .start("s3://my-bucket/delta/events")

query.awaitTermination()
```

> **Mastery Note:** The `maxOffsetsPerTrigger` option is enforced by `KafkaMicroBatchReader.planInputPartitions()`, which distributes the cap proportionally across all partitions — if you have 100 Kafka partitions and set `maxOffsetsPerTrigger = 500000`, each partition reads at most 5,000 records. This means Spark task parallelism equals your Kafka partition count, so **under-partitioned Kafka topics are the number-one cause of under-utilization in streaming jobs**: 10 Kafka partitions = 10 parallel tasks maximum, regardless of executor count. The async progress tracking config eliminates the WAL commit latency (~50–200ms on S3) from the critical path, delivering measurable throughput improvement on triggers firing every 10–30 seconds.

### Example 2: RocksDB State Store Configuration for High-Cardinality Stateful Aggregation

> **What this demonstrates:** Production-grade RocksDB state store configuration for a high-cardinality streaming aggregation that would OOM with the default `HDFSBackedStateStore`, showing every tunable knob with its JVM/off-heap memory implication.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, window, count, sum as spark_sum, expr

spark = (SparkSession.builder
    .appName("RocksDB-StatefulAggregation")
    # Switch state store provider from in-memory HDFS to RocksDB
    # This moves state from JVM heap to off-heap native memory + local NVMe
    .config("spark.sql.streaming.stateStore.providerClass",
            "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider")
    # Block cache: LRU cache for RocksDB SST block reads — kept in off-heap native memory
    # Default is 8MB — catastrophically small for >1M state keys; use 512MB–2GB
    .config("spark.sql.streaming.stateStore.rocksdb.blockCacheSize", "1073741824")  # 1GB
    # Write buffer: MemTable size before flush to SST — larger = fewer compactions
    # Default 64MB causes stalls under >10K writes/second per partition
    .config("spark.sql.streaming.stateStore.rocksdb.writeBufferSizeMb", "256")
    # Number of MemTables before write stall — gives compaction thread time to catch up
    .config("spark.sql.streaming.stateStore.rocksdb.maxWriteBufferNumber", "4")
    # Bloom filter bits per key: higher = fewer false positives = fewer disk reads for misses
    # 10 bits/key is the standard Bloom-filter sweet spot (1% false positive rate)
    .config("spark.sql.streaming.stateStore.rocksdb.bloomFilterBitsPerKey", "10")
    # Upload state snapshot to checkpoint dir every N commits, not every commit
    # Reduces S3/GCS upload cost and latency by 50–90% for large state partitions
    .config("spark.sql.streaming.stateStore.rocksdb.enableCommitStatsDuration", "true")
    # Parallelism for RocksDB background compaction threads per executor
    # Set to number of NVMe drives or half of executor cores, whichever is smaller
    .config("spark.sql.streaming.stateStore.rocksdb.maxBackgroundJobs", "4")
    # Enable changelog checkpointing: upload only the WAL delta, not full state snapshot
    # Reduces checkpoint upload time from O(state_size) to O(batch_writes) — critical for large state
    .config("spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled", "true")
    # Executor memory: leave headroom for RocksDB block cache (off-heap) + task execution
    .config("spark.executor.memory", "8g")
    .config("spark.memory.offHeap.enabled", "true")
    .config("spark.memory.offHeap.size", "2g")  # additional off-heap for Tungsten
    .getOrCreate())

events = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "user-events")
    .option("maxOffsetsPerTrigger", 1000000)
    .load()
    .selectExpr(
        "CAST(key AS STRING) AS user_id",
        "CAST(value AS STRING) AS event_type",
        "timestamp AS event_time"
    ))

# Watermark must be set BEFORE the stateful groupBy
# Without it, state for every window key accumulates forever → guaranteed OOM
windowed = (events
    .withWatermark("event_time", "30 minutes")
    .groupBy(
        col("user_id"),
        # Tumbling window: 5-minute non-overlapping windows
        # State holds one entry per (user_id, window) pair
        window(col("event_time"), "5 minutes")
    )
    .agg(
        count("*").alias("event_count"),
        spark_sum(expr("CASE WHEN event_type = 'purchase' THEN 1 ELSE 0 END"))
          .alias("purchase_count")
    ))

(windowed.writeStream
    .format("delta")
    .outputMode("append")   # Append mode: only emit completed windows (after watermark passes)
    .option("checkpointLocation", "/mnt/nvme/checkpoints/windowed-agg")
    .trigger(processingTime="60 seconds")
    .start("/mnt/delta/user-window-agg"))
```

> **Mastery Note:** The `changelogCheckpointing.enabled` configuration is the single highest-impact RocksDB tuning for jobs with >1GB state per partition. Without it, every trigger uploads the **entire** RocksDB snapshot to the checkpoint directory — a 10GB state partition means 10GB of S3 uploads every 60 seconds, which costs ~$4,000/month in egress alone and adds 30–90 seconds of checkpoint latency to every trigger. With changelog checkpointing enabled, only the RocksDB WAL entries (typically 1–50MB per trigger) are uploaded, reducing checkpoint I/O by 99%. The `outputMode("append")` is mandatory with event-time windowing and watermarks — `outputMode("update")` would re-emit every intermediate window state on every trigger, causing massive downstream write amplification.

### Example 3: Stream-Stream Join Tuning with Stateful Join State Expiry

> **What this demonstrates:** How stream-stream joins buffer both sides in state store partitions and how precisely calibrated watermarks and join conditions prevent the state buffers from growing unboundedly — the most operationally complex stateful pattern in Structured Streaming.

```scala
import org.apache.spark.sql.SparkSession
import org.apache.spark.sql.functions._
import org.apache.spark.sql.streaming.Trigger
import scala.concurrent.duration._

val spark = SparkSession.builder()
  .appName("StreamStreamJoin-Tuned")
  .config("spark.sql.streaming.stateStore.providerClass",
    "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider")
  // Stream-stream joins create TWO state stores per partition (one per side)
  // With 200 shuffle partitions and 2 sides, that is 400 concurrent RocksDB instances
  // Reduce shuffle partitions aggressively for streaming to cut state store overhead
  .config("spark.sql.shuffle.partitions", "100")
  .getOrCreate()

import spark.implicits._

// LEFT SIDE: ad impressions stream — an ad was shown to a user
val impressions = spark.readStream
  .format("kafka")
  .option("kafka.bootstrap.servers", "broker:9092")
  .option("subscribe", "ad-impressions")
  .option("maxOffsetsPerTrigger", 200000)
  .load()
  .selectExpr("CAST(value AS STRING) AS json")
  .select(
    get_json_object($"json", "$.impression_id").alias("impression_id"),
    get_json_object($"json", "$.user_id").alias("user_id"),
    (get_json_object($"json", "$.timestamp").cast("long") / 1000)
      .cast("timestamp").alias("impression_time")
  )
  // Watermark on impressions: tolerate up to 2 hours of late data from ad servers
  // This watermark bounds how long we buffer impression-side state
  .withWatermark("impression_time", "2 hours")

// RIGHT SIDE: click events stream — user clicked on an ad
val clicks = spark.readStream
  .format("kafka")
  .option("kafka.bootstrap.servers", "broker:9092")
  .option("subscribe", "ad-clicks")
  .option("maxOffsetsPerTrigger", 50000)
  .load()
  .selectExpr("CAST(value AS STRING) AS json")
  .select(
    get_json_object($"json", "$.impression_id").alias("impression_id"),
    get_json_object($"json", "$.click_time").cast("timestamp").alias("click_time")
  )
  // Watermark on clicks: tolerate up to 30 minutes of late click events
  // The GLOBAL watermark = min(impression watermark, click watermark)
  // So the more lenient side (2 hours) dominates state retention time
  .withWatermark("click_time", "30 minutes")

// Stream-stream join: match impressions to their corresponding clicks
// The join condition MUST include an event-time range constraint
// Without it, Spark cannot bound state eviction and throws an AnalysisException:
// "Stream-stream join without a watermark is not supported in append mode"
val attributed = impressions.join(
  clicks,
  // Equi-join on impression_id — determines shuffle partition for both state stores
  impressions("impression_id") === clicks("impression_id") &&
  // Time-range constraint: click must occur within 1 hour of impression
  // This is the hard upper bound on how long impression-side state rows are retained
  clicks("click_time") >= impressions("impression_time") &&
  clicks("click_time") <= impressions("impression_time") + expr("INTERVAL 1 HOUR"),
  "leftOuter"  // leftOuter: emit unmatched impressions as null-click after watermark passes
)

attributed.writeStream
  .format("delta")
  .outputMode("append")
  .option("checkpointLocation", "s3://bucket/checkpoints/attribution")
  .trigger(Trigger.ProcessingTime(30.seconds))
  .start("s3://bucket/delta/attributed-clicks")
```

> **Mastery Note:** In a stream-stream join, Spark's Physical Planner generates a `StreamingSymmetricHashJoinExec` node that maintains **two** `StateStore` instances per shuffle partition: one buffering the left-side (impression) rows and one buffering the right-side (click) rows not yet matched. State eviction is triggered by the **minimum of the two watermarks** — so if impressions lag by 2 hours and clicks lag by 30 minutes, the effective watermark advances at the pace of the 2-hour side. This means impression state rows are retained for up to `2 hours + 1 hour (join range)` = 3 hours, which at 200K impressions/sec equates to 2.16 billion buffered rows. The `spark.sql.shuffle.partitions` reduction from 200 to 100 halves the number of state store instances, which directly halves RocksDB memory overhead and compaction thread count — this is one of the most impactful and most frequently overlooked streaming tuning steps.

### Example 4: Async Progress Tracking + `flatMapGroupsWithState` with Manual State TTL

> **What this demonstrates:** How to implement arbitrary stateful logic with `flatMapGroupsWithState`, enforce manual state TTL to prevent unbounded growth, and combine it with async progress tracking to achieve sub-second trigger-to-trigger latency — an advanced pattern used in real-time session analytics.

```python
from pyspark.sql import SparkSession
from pyspark.sql.functions import col, expr
from pyspark.sql.streaming import GroupStateTimeout
from pyspark.sql.types import (StructType, StructField, StringType,
                                LongType, TimestampType, BooleanType)
import time

spark = (SparkSession.builder
    .appName("SessionAnalytics-AsyncTracking")
    .config("spark.sql.streaming.stateStore.providerClass",
            "org.apache.spark.sql.execution.streaming.state.RocksDBStateStoreProvider")
    # Async progress tracking: WAL offset commit happens in a background driver thread
    # The next batch's constructNextBatch() begins immediately after processing completes
    # rather than waiting for the checkpoint write — reduces inter-trigger gap by 15-40%
    .config("spark.sql.streaming.asyncProgressTrackingEnabled", "true")
    # How often the async thread actually flushes to the checkpoint store
    # 30s means we tolerate replaying up to 30s of offsets on driver restart
    .config("spark.sql.streaming.asyncProgressTrackingCheckpointIntervalMs", "30000")
    # Continuous shuffle partition reduction for streaming
    .config("spark.sql.shuffle.partitions", "50")
    .config("spark.sql.streaming.stateStore.rocksdb.changelogCheckpointing.enabled", "true")
    .config("spark.sql.streaming.stateStore.rocksdb.blockCacheSize", "536870912")  # 512MB
    .getOrCreate())

# State schema: tracks active session metadata per user
# Python dataclasses cannot be used here — must use tuples or NamedTuples
from typing import Iterator, Tuple
from pyspark.sql.streaming import GroupState

SESSION_TIMEOUT_MS = 30 * 60 * 1000  # 30-minute inactivity timeout

def update_session_state(
    user_id: str,
    events: Iterator,
    state: GroupState
) -> Iterator:
    """
    Called once per (user_id, trigger) with all events for that user in this batch.
    State layout: (session_start_ms, last_event_ms, event_count, is_converted)
    """
    current_ms = int(time.time() * 1000)

    if state.hasTimedOut:
        # GroupStateTimeout.ProcessingTimeTimeout fired — session expired
        # Emit the final session record and remove state to prevent accumulation
        if state.exists:
            sess = state.get  # returns the tuple we stored
            yield (user_id, sess[0], sess[1], sess[2], sess[3], True)  # is_final=True
        state.remove()  # CRITICAL: without this, timed-out state is never evicted
        return

    # Merge all events in this micro-batch for this user_id
    event_list = list(events)
    event_count_delta = len(event_list)
    is_converted = any(e["event_type"] == "purchase" for e in event_list)

    if state.exists:
        # Continue existing session — update last_event_ms and counters
        sess = state.get
        new_state = (
            sess[0],                              # session_start_ms: unchanged
            current_ms,                           # last_event_ms: refreshed
            sess[2] + event_count_delta,          # event_count: incremented
            sess[3] or is_converted               # is_converted: sticky once True
        )
    else:
        # New session for this user — initialize state
        new_state = (current_ms, current_ms, event_count_delta, is_converted)

    state.update(new_state)

    # Reset the processing-time timeout on every event — classic session window pattern
    # If no events arrive for SESSION_TIMEOUT_MS, the state will time out
    state.setTimeoutDuration(SESSION_TIMEOUT_MS)

    # Yield intermediate progress record (outputMode must be "update" for mid-session rows)
    yield (user_id, new_state[0], new_state[1], new_state[2], new_state[3], False)

# Define output schema explicitly — Catalyst cannot infer from generator functions
output_schema = StructType([
    StructField("user_id",           StringType(),   False),
    StructField("session_start_ms",  LongType(),     True),
    StructField("last_event_ms",     LongType(),     True),
    StructField("event_count",       LongType(),     True),
    StructField("is_converted",      BooleanType(),  True),
    StructField("is_final",          BooleanType(),  True),
])

events_df = (spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "user-activity")
    .option("maxOffsetsPerTrigger", 300000)
    .load()
    .selectExpr(
        "CAST(key AS STRING) AS user_id",
        "CAST(value AS STRING) AS event_type"
    ))

sessions = (events_df
    .groupBy("user_id")
    # ProcessingTimeTimeout: timeout fires based on wall-clock, not event-time
    # Use EventTimeTimeout only when data has reliable, monotonically-increasing timestamps
    .flatMapGroupsWithState(
        output_schema,
        GroupStateTimeout.ProcessingTimeTimeout,
        update_session_state
    ))

(sessions.writeStream
    .format("delta")
    .outputMode("update")   # Must be "update" — "append" is not supported with arbitrary state
    .option("checkpointLocation", "/mnt/nvme/checkpoints/sessions")
    .trigger(processingTime="10 seconds")   # Short trigger: session analytics needs low latency
    .start("/mnt/delta/sessions"))
```

> **Mastery Note:** `flatMapGroupsWithState` with `ProcessingTimeTimeout` is the only pattern in Structured Streaming that allows true session-window semantics with inactivity-based expiry — event-time windows cannot express "fire after 30 minutes of silence" because they are driven by watermarks, not wall-clock time. The `state.remove()` call inside the timeout branch is non-negotiable: if you emit the final session record but forget to call `state.remove()`, the state entry remains in RocksDB indefinitely, consuming disk and causing compaction to process ever-growing SST levels. In production, instrument `state.getOption.isDefined` rates via custom Dropwizard metrics (accessible via `TaskContext.get().taskMetrics()`) to detect state accumulation bugs before they become OOM events. The async progress tracking configuration reduces the inter-trigger gap from `~150ms (S3 WAL commit)` to `~5ms` on 10-second triggers, directly translating to lower end-to-end event latency at the 99th percentile.

## 📚 Summary

Structured Streaming performance tuning is a multi-layered discipline that spans the entire Spark execution stack. At the source layer, `maxOffsetsPerTrigger` is the primary backpressure mechanism — it prevents trigger stacking by hard-capping how much data enters each micro-batch, allowing the job to drain accumulated Kafka lag gradually rather than attempting to process it all in one catastrophic batch. The trigger interval selection balances latency requirements against cost: shorter triggers mean lower end-to-end latency but higher per-record overhead from fixed-cost operations like WAL commits and state store snapshots, which async progress tracking partially amortizes by decoupling checkpoint writes from the batch processing critical path.

At the state store layer, migrating from `HDFSBackedStateStore` to `RocksDBStateStoreProvider` is the most impactful architectural change available for stateful streaming jobs. It transforms state management from a heap-exhausting JVM problem into a well-understood LSM storage problem, at the cost of requiring careful RocksDB configuration: block cache sizing, write buffer tuning, and compaction thread allocation must all be sized against the actual state cardinality and write throughput of the specific workload. Changelog checkpointing then makes the checkpoint upload cost proportional to write volume rather than total state size, unlocking the ability to maintain terabytes of state while still committing checkpoints within the trigger interval.

At the join and aggregation layer, watermark precision is the master control variable. Every stateful operator's memory footprint is directly proportional to the watermark delay: a 2-hour watermark in a stream-stream join buffers 2 hours of left-side events per partition. Instrumenting `inputRowsPerSecond`, `processedRowsPerSecond`, `triggerExecution` duration, and RocksDB compaction metrics via the `StreamingQueryListener` API transforms streaming performance from reactive firefighting into proactive, data-driven capacity management — which is the defining characteristic of production-grade Spark streaming engineering.
